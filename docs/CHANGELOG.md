**M2b 的三重护栏**（防止模型幻觉污染字幕）：

1. **必须有热词依据**：`matched_hotword` 不在词表里的候选，直接丢弃。这条把
   「润色型建议」和「臆造修改」全部挡在队列外。
2. **原文必须逐字定位**：`original` 在该句 token 流里找不到就拒绝。
   模糊匹配会改错位置，所以宁可不做。
3. **不改动时间轴**：`apply_replacement` 只允许区间内重排，区间首尾毫秒不变；
   跨边界、空替换、时间倒挂一律抛错。

**真实 LLM 验证**：植入一处同音错写「剧集标签」（正确应为「句级标签」），
模型输出**恰好一条**候选、置信度 0.95、零误报，消耗 454 prompt token。

**M2b 修掉的真实缺陷**：

- `shift_ranges_after` 在「编辑点正好落在句子起点」时会把整句平移，
  导致编辑点从所有句子区间里漏掉（违反 INV-1）。改为只有句尾移动。
- 兼容模式端点路径写错（`/api/v1/compatible-mode/...` → 404），
  正确是域名根下的 `/compatible-mode/v1`。
- 测试数据 `sizes=[4,4]` 与 7 字文本不匹配，暴露了区间校验缺失。

**验证**：242 个单测通过（新增 60 个），3 个 live 测试（转写/抽词/校对）全过。


## M3 校正台（2026-11-05）

### 后端补的两块

**波形峰值（`media/peaks.py`）**：3 小时音频解码成 float PCM 约 1.9GB，
浏览器直接 `decodeAudioData` 必崩（§7.1）。改为后端一次解码、逐级降采样成
min/max 桶，写入 `PKC1` 二进制缓存（键是媒体 sha256，不是文件名）。

| 级别 | 用途 |
|---|---|
| 8 buckets/s | 全览 |
| 64 | 默认视图 |
| 512 / 4096 | 放大到词级 |

**编辑接口（`services/editing.py`）**：句边界（另起一句/并入上下句/合并）、
文字修改、撤销。句边界与文字修改用不同 `op_type` 分开记录——这是 §6.4 的要求，
否则无法统计「哪类错误最多」。

### 前端要点

- **波形不用 wavesurfer 解码路径**，只用 canvas 画后端给的桶；播放用原生
  `<audio>` + HTTP Range，拖动不重下整文件。
- **词级选择是 token 点击/拖拽**，不是 DOM 选区。所有编辑都归约为 token 区间运算，
  contenteditable 的选区模型对不上（§7.3）。
- **文字修改必须基于选区**：后端在 token 流里逐字定位 `original`，而标点存在
  `punc_after` 而非 token 文本里，所以整句文本（含标点）永远定位不到。
  要求先选字，从构造上保证请求可定位。
- 快捷键：空格播当前句、`[` `]` 上下句、`Esc` 清选区。

### M3 修掉的真实缺陷（很重要）

**同字数替换会移动内部时间边界。** 把「句级」改成「句集」（2 字换 2 字），
原时间 `14800–14960 / 14960–15200` 被重新插值成 `14800–15000 / 15000–15200`。
音频根本没变，用户听到的切点却漂了 40ms。

根因：`apply_replacement` 只校验区间**首尾**边界，中间 token 的边界被
按字符数重新分配。修正为「同字数替换逐位复用原时间」，并把不变量加严为
**区间内每个 token 的边界都必须不变**。

这个 bug 单测没抓到——原有测试只断言了首尾和整体文本。现在补了两个回归测试，
其中一个用真实 ASR 那种不均匀的字词时长（180/220/600ms）来验证。

### 前端测试

`node --test src/logic.test.mjs`：9 条用例覆盖选区语义、活动句判定、CPS 计算、
半开区间边界。加它是因为 tsc 抓不到「参数个数对但值错」这类 bug——
文字修改按钮一度把 `undefined` 当 `proposed` 发给后端。

### M3 补充：键盘导航与边界拖动（用户反馈后）

**修掉三个真实 bug**

1. **音频根本播不了，导致快捷键像没实现。** 音频接口把 WAV 硬编码成
   `Content-Type: audio/mpeg`，浏览器拒绝解码，`play()` 静默失败。
   `[ ]` 的键盘处理器一直是对的，只是没有任何声音。
   顺带修了另外两点：`Response` 本身不处理 Range（只声明 `Accept-Ranges`
   是假的），以及 `read_bytes()` 每次请求都把整个文件读进内存。改用
   `FileResponse` + 按 codec 推断 MIME。

2. **`[ ]` 在句间静音处失效。** 原来用 `activeOrd` 定位，而播放头落在句间
   空白时 `activeOrd === -1`，`findIndex` 返回 -1，`-1 + 1 = 0`——
   两个方向都跳到第一句。改为按时间位置查找（`sentenceAtOrBefore`），
   并让 `[` 先回退到当前句开头、再退到上一句。

3. **空格键被按钮抢走。** 按钮点击后保持焦点，空格触发的是按钮而不是播放。
   现在按钮聚焦时空格/回车交还给按钮，其余情况才归播放；同时忽略输入法
   组字状态（中文输入法会吞掉 `[` `]`）。

**新增能力：在波形上拖动句边界**

设计取舍：
- 只有**句首首字**和**句末尾字**可拖。中间的 token 不可拖——移动它会
  让句子自身的区间失效，波形拖动给不出合理的修复方式。
- 拖动只改**被拖的那个 token**，其他 token 一个毫秒都不动。
  这是用户明确要求的，也是唯一安全的语义。
- 越界自动夹紧并说明原因（「不能晚于 400ms（会与相邻字重叠）」），
  而不是静默忽略——用户需要知道为什么拖不动。
- 拖动后该 token 的 `derived` 置为 false：它不再是从 ASR 插值来的，
  而是人定的。

实测（真实数据）：把句 0 末字从 `2660–2920` 拖到 `2660–3040`，
61 个 token 中**只有 idx=11 变化**，句 1 的 `3840–6080` 完全未动。

## M4 剪辑（2026-11-05）

### 核心：EDL 与时间轴重映射

`core/edl.py` 是纯函数层，两条不可妥协的性质：

1. **删除集是唯一真相，保留段是推导出来的。** 用户删东西，不是指定保留什么。
   推导意味着撤销一次删除只需删掉那条记录，不需要重建任何东西。
2. **成片之后所有时间都要过 `TimeMap`。** 字幕、章节、文稿导出引用的都是
   原始时间轴；不映射就会每删一次、偏差再累积一次。

`TimeMap` 提供 `to_new`（原文→成片）、`to_old`（成片→原文）双向，
以及 `to_new_clamped`（被删瞬间吸附到最近保留点，用于字幕 cue 起点落在删除区的情况）
和 `map_range`（整段映射，全被删则返回 None）。

### 渲染（`media/render.py`）

- 每个片段**必须**加 5ms 淡入淡出。不加就是 PCM 阶跃，拼接头必然爆音。
  这不是音效处理，是剪辑正确性的一部分。
- 段数多时命令行会超长，filtergraph 写文件传给 `-filter_complex_script`。
- 输出沿用源采样率与声道——这是交付物，不是 ASR 输入，降采样等于丢用户已有的质量。
- 渲染结果按 `edl_signature` 缓存，同一份 EDL 不重复编码两小时的音频。
- **渲染必须异步**（`services/renders.py`）。实测：105 分钟素材、400 段，
  编码耗时约 12 分钟。同步实现有两个必然后果，而且都真实发生过：
  按钮十二分钟没有任何反馈（用户报的就是「点击后无反应」）；
  整个编码期间持有一个 SQLite 写事务，其他任何写操作都 `database is locked`。
  现在是「短事务记录任务 → 工作线程跑 ffmpeg → 短事务写进度」，
  `POST /render` 0.35s 返回，`GET /api/renders/{id}` 轮询 `progress`。
  进度取自 ffmpeg 的 `-progress` 流（`out_time_ms` 实际是微秒）。它是**编码吞吐**，
  不能按成片时长反推剩余时间：本机编码约为实时的 8 倍。

### 实测结果（真实音频，17.6s）

删除第 2 句（3709–6080ms）后：

| 项 | 值 |
|---|---|
| EDL 预期成片 | 15306ms |
| 实际文件时长 | **15306ms（误差 0ms）** |
| 段落数 | 2 |
| 静音吸附 | 末尾 6080ms → 5971ms（吸附到静音起点） |
| 时间轴映射 | 被删句 → `None`；后续句全部精确前移 2302ms |
| 恢复删除后 | 精确回到 17608ms，1 段 |

### M4 修掉的真实缺陷

**`to_new` 把删除区间的第一个瞬间映射回保留段末尾。**
keep 是半开区间 `[orig_start, orig_end)`，当 `ms == keep.orig_end` 时原实现
返回 `keep.new_end`，于是「已被删除的瞬间」得到一个有效的新时间。
后果是字幕 cue 本该消失，却提前一帧重新出现——静默、且随着删除变多而累积。

修正为：边界瞬间若属于下一个 keep，就由下一个 keep 处理；否则返回 `None`。

（另有一个低级错误：渲染命令漏了输出路径，ffmpeg 写到 stdout 后「成功」返回，
磁盘上什么都没有。已修，并补了时长断言测试。）

### 测试

后端 337 个（新增 49 条：区间代数 20、时间映射 12、过滤图与真实渲染 17），
前端 20 条。渲染时长断言容差 50ms——AAC 有约 20ms 的 encoder delay，
超过这个量级就意味着字幕会肉眼可见地漂移。

### M4 补充：实时预览与整句选区（用户反馈后）

**1. 实时预览删除效果 —— 不做渲染，做「跳过式播放」**

用户的原话是每次都要渲染成片才能判断删除是否合理。这个问题必须解决，
因为渲染一小时节目要几分钟，尝试性剪辑根本没法用。

比较了三种方案：

| 方案 | 每次改动的延迟 | 问题 |
|---|---|---|
| 每次改动渲染预览 | 5–60s | 探索性剪辑不可用 |
| 预渲染整条时间轴 | 几分钟 | 每次编辑都失效 |
| **跳过式播放** | **0ms** | 最多漏出 1 个轮询间隔的音频 |

采用第三种：播放时若播放头落入删除区间，直接 seek 到区间末尾。

- 用 50ms 轮询而非 `timeupdate`：后者在部分浏览器被节流到 250ms，
  会漏出至多四分之一秒的被删内容。
- **相邻删除区间必须合并**，否则一串删除会触发多次 seek，听起来像卡顿。
- seek 落入删除区时自动前移到最近的存活位置，否则用户点波形会听到空白。

代价是播放头位置在跳切处不连续，UI 上以波形红色区域标示，用户能预期。

**2. 整句选区**

两种选区并存，且互相排斥：

- **词级选区**（token 区间）：重划边界、改错字、删词。
- **整句选区**（`Set<ord>`）：整句并入上下句、多句批量删除。

分开存而不是互相推导，是因为「选 5 句一起删」应该是点第一下和最后一下，
而不是拖过 300 个字。点字会清空句选区、点句会清空字选区，操作栏永远只有
一个明确目标。

按钮启用条件按选区类型推导（此前几个按钮用同一个 `!selection` 判断，
导致整句选中时按钮全灰）：

| 按钮 | 需要什么 | 为什么 |
|---|---|---|
| 另起一句 | 仅词级、且在一句内 | 整句已是独立一句，再切无意义 |
| 并入上句/下句 | 词级在句内，或任意整句 | 整句时退化为合并 |
| 合并选区 | 任意 | — |
| 删除选中 | 任意 | 多句会合并成一个删除区间 |

**3. 一个排查记录**

多句删除测试时 EDL 里出现了两个删除区间，一度怀疑是吸附或 guard 造成的。
查库确认是历史遗留的有效删除记录，`removed=1` 的软删除记录被正确排除。
结论：数据无问题，`soft delete` 生效正常。这条记录下来是因为
「两个区间」看起来很像 bug，实际是测试数据未清理。

## 工作台界面与导航修复（2026-11-05）

### 界面重构为三区工作台

```
┌────────────────────────────────────────────────────────┐
│ Animatter  项目  设置  导出         项目名 · v1        │  菜单栏
├──────────────┬─────────────────────────────────────────┤
│ 热词         │ 时间码 · 句/字数 · 成片时长             │
│ 本期/全局    ├─────────────────────────────────────────┤
├──────────────┤ 波形 + 字幕叠加（点击字幕跳该句）        │
│              │                                         │
│ 字幕校对     ├─────────────────────────────────────────┤
│ （句列表）   │ ▶ 播放 ⟨上一句 下一句⟩ 删除 恢复 导出     │
│              ├─────────────────────────────────────────┤
│              │ 另起一句 并入上句 并入下句 合并选区      │
├──────────────┤                                         │
│ 操作记录     │ 提示 / 成片试听                          │
└──────────────┴─────────────────────────────────────────┘
```

布局原则：
- 左栏固定 340px。字幕是密集内容，需要稳定列宽；波形每多一像素都有用。
- 只有字幕列滚动，热词与操作记录固定。两者都是「随时瞟一眼」的信息，
  滚动出去就等于没有。
- 波形上部 22px 是字幕带，文字不遮住它描述的波形。字幕按自身时间区间裁剪，
  长句不会溢出到邻句。
- 字幕可点击 → 播放该句。

### 设置

单行 JSON 存 `setting` 表，而不是一列一个配置项：可调项会持续增加，
blob 让新增一项不需要迁移。

校验必须**大声失败**。未知键直接报错而不是存下来——静默忽略一个设置项，
在用户看来和「这个功能坏了」没有区别。
实测：未知键 400、越界值 400、枚举值非法 400。

菜单按「何时生效」分组，因为这才是用户需要知道的：
模型类改动要重新转写，剪辑参数影响下次渲染，导出选项只在导出时生效。
混在一起会让人以为换个 ASR 模型就能修正已有转录。

### 操作记录

可撤销性按 op 类型区分，且**在 UI 里说明原因**：灰掉一行不解释，看起来就是 bug。

| 操作类型 | 可撤销 | 原因 |
|---|---|---|
| boundary（重划边界） | ✅ | 存了完整句子快照 |
| text（改文字） | ❌ | 会改变 token 数，需反向替换 |
| boundary_time（拖边界） | ❌ | 同上，且后续编辑已基于新时间 |

**只能撤销最近一次边界操作。** 更早的操作之后若还有别的编辑，
回滚它会用一份过期快照覆盖掉那些改动。这条限制在服务层强制，
实测越序撤销会报「只能撤销最近一次边界操作」。

### 修复两个导航 bug

用户报告的两个现象，根因是同一个：**导航不知道句子已被删除**。

**bug 1：点击静默区后按空格没声音。**
播放头落在句间空白（或删除区）时，`sentenceAtOrBefore` 返回的是前一句，
而前一句已被删除 → 起点在删除区内 → `playRange` 的停止点在起点之前
→ 立即暂停，表现为「按了没反应」。

**bug 2：前一句已删除时，点上一句或按 `[` 没反应。**
`playPrevious` 取 `sentences[current - 1]`，那正是被删的句子；
`seek` 到删除区内是空操作（`nextAudible` 会把它推回到同一位置）。

修法是把导航从「列表索引」改为「存活音频中的位置」（`navigation.ts`）：
- `previousSentence` / `nextSentence` 跳过整句被删的句子。
- `audibleStart` 对整句被删返回 `null`，部分被删则前移到存活部分。
- `audibleStop` 保证停止点严格在起点之后，否则返回 `null` 表示「播到自然结尾」。
- 全部更早的句子都删完时，`[` 回到第一处存活音频，而不是原地不动。

新增 12 条测试覆盖这些情况，包括相邻删除区间、部分删除、越界回退。

## 工作台与 M5a 字幕导出（2026-11-05）

### 修掉的界面缺陷：菜单和面板全透明

根因不是配色，是 **`--surface` 这个 CSS 变量从未定义**：

```css
/* styles.css 用了 3 次，定义处 0 次 */
background: var(--surface);
```

未定义的自定义属性会让整条声明在 computed-value 阶段**失效**，于是背景变成
`transparent`，下拉菜单和模态框直接透出背后的工作区文字。

修法：定义 `--surface`（浅色 `#ffffff` / 深色 `#1a2334`），并给所有引用加
兜底 `var(--surface, var(--panel))`——将来再写错一个变量名，退化成面板色而不是
"透明"这种最难排查的表现。

顺带补了 `--accent-dark`（同样被引用但未定义，chip 文字因此用了无效色）。
已加变量审计：任何 `var(--x)` 若无定义都会立刻暴露。

### 项目存档（`.project`）

设计目标不是"导出"，而是**可继续剪辑的存档**。因此归档必须携带：
文稿、每个句子边界、每处文字修正、每处删除、**完整操作记录**、热词、大纲、校对候选。

**刻意不携带音频**：两小时 WAV 是 GB 级，存档要能塞进邮箱附件。改为记录
`sha256`，载入时按哈希重新关联。三种情况：

| 情况 | 行为 |
|---|---|
| 文件在且哈希一致 | 正常关联 |
| 文件在但哈希不符 | 仍关联，并警告时间轴可能与音频不匹配 |
| 文件不在 | 用占位 media 行恢复文稿与全部编辑，提示重新关联音频 |

第三种是关键取舍：**音频丢了不能连带丢掉用户的剪辑工作**。

格式是 zip 包里的 `project.json`：任何工具都能读，transcript 压缩率高。
载入**永远新建项目**而不是覆盖——覆盖用户正在编辑的项目是不可恢复的。

### 修掉存档路径上的 4 个真实缺陷

写这个功能时踩到的，全部是"只有真正跑一遍才会发现"的类型：

1. **`sentence.updated_at` NOT NULL 未赋值** → 载入直接 500。
2. **`token.id` 是 INTEGER AUTOINCREMENT**，却传了 `tok_xxx` 字符串 →
   `sqlite3.IntegrityError: datatype mismatch`。
3. **`media.sha256` 全局唯一**，存档里带着原哈希再插一行必然冲突 →
   改为：已有同哈希行则复用；文件缺失时用 `missing:<random>` 合成哈希。
4. **`--surface` 未定义**（见上）。

教训：模型层每个 `NOT NULL` 列都应该在恢复路径上有明确来源。已按表核对一遍
（token / sentence / edit_op / deletion / episode_hotword / outline /
correction_candidate / transcript_version）。

### 吸附的单调性（顺带修掉的一个语义 bug）

`sanitize` 的静音吸附原来会挑"最近的静音边界"，**不看方向**，于是能把切点
往里挪：

```
用户删到 6010，附近静音 5991–6100  →  实际删到 5991（少删了 19ms）
```

这等于把用户明确要删的音频还回来，而且恰恰留下了吸附本要消除的半截音素。
现在强制单调：**start 只能左移、end 只能右移**，吸附永远只会扩大删除范围。
补了两条回归测试。

### M5a 字幕导出

- SRT / VTT / TXT 三种格式。TXT 就是"自动整理的文稿"初版（一行一句，无时间码）。
- **所有时间戳都过 `TimeMap`**。实测：删掉第 2 句后，第 3 句字幕从
  `00:00:06,440` 变成 `00:00:04,138`，与成片音频对齐；未映射版本仍是 6.44s。
- 没有删除时返回 `None` 而不是恒等映射——恒等映射也要经过一次浮点运算，
  没必要时不该引入舍入机会。
- 长句按标点优先拆分成多条字幕（`max_chars × max_lines` 预算），拆完按字符数
  比例分配原有时间，不改变句子总时长。
- 质量检查：`too_fast`（超语速）、`too_brief`（<0.4s）、`split`、`partially_deleted`，
  在导出前就显示给用户，而不是等播放时才发现。

### 修掉 `media.sha256` 全局唯一导致项目「没有音频」（2026-11-06）

用户报「这个项目没有登记音频文件」。排查发现是**约束与归属模型自相矛盾**：

```sql
sha256 VARCHAR(64) NOT NULL UNIQUE   -- 全局唯一
project_id VARCHAR(64) NOT NULL      -- 但按项目归属
```

执行链：

1. `register_media` 把音频**复制**到 `data/projects/<project_id>/media/`，
   说明媒体行是项目私有的。
2. 但查找复用时按 `sha256` 全局匹配 → 载入存档时命中了**另一个项目**的行，
   直接 `return`。
3. 结果：新项目的 `version.media_id` 指向别人的 media 行，自己一条都没有。
4. `/api/projects/{id}/media` 按 `project_id` 过滤 → 返回 `[]`。
5. 前端看到空列表 → 「这个项目没有登记音频文件」。

**修复**：
- 约束改为 `UNIQUE (project_id, sha256)`，`sha256` 单独建索引。
- `register_media` 与存档恢复的复用查询都加上 `project_id` 过滤。
- 迁移用原始 SQL 重建表（SQLite 不支持 `DROP CONSTRAINT`，且原约束是
  **未命名内联**的，Alembic 无法按名删除）。

**为什么这不只是数据脏**：只要用户把同一段音频用在两期节目（试听样本、
片头音乐、同一期重剪），旧约束就必然让第二个项目失去自己的媒体行。
这是设计层面的矛盾，不是偶发。

**验证**：存档往返后新项目 `media=1`、`duration=17608ms`、5 句一致；
前端启动序列经 Vite 代理全部 200，音频 Range 返回 `206 audio/wav`。

## 词级编辑与说话人（2026-11-06）

### 决策：从字级退回词级

需求原话：「咱们彻底不要求字级了，就只管词级。字幕区点击文字换成是按一个一个词来框选。」

**推翻的旧设计**：`_split_units` 把每个 ASR 词按字符切开，词的时长按字符数比例插值，
每个字得到一段**观测不出来的时间**，标 `derived=1`。

**为什么必须推翻**（两层，第二层才是决定性的）：

1. 字级时间不存在。字级粒度误差 = 词时长 / 字数，中文典型 60–200ms/字。
2. 因此"改字"变成一次**重新插值**：新旧字数不同就必然重排窗口内部的时间点。
   实测 `14800–14960 / 14960–15200` 被改成 `14800–15000 / 15000–15200`——
   用户改了一个错别字，他正在听的剪切点挪了 40ms。这类 bug 无法靠加断言根治，
   因为**边界本来就该动**：字数变了，比例分配就得变。

词级把这类 bug 从"需要小心"变成"结构上不存在"：一个 token 就是一个观测区间，
替换永远 1 token → 1 token，两条边都是真的，内部没有可移动的点。

**代价**：选择粒度变粗，改不了半个词；想剪掉词中间只能波形框选。

**连带结论（用户提问的直接回答）**：「改文字是否就不用严格要求字数一致了？」
——**是的**。词级下替换文本可以任意长（"人工智能" → "AI" 合法）。唯一保留的是
一个**可读性提示**：新文本按原词时长算出来的语速超过 ~14 字/秒时告诉用户
"要塞进 90ms，语速会明显快于原音"，但不阻止。

### 决策：修正与删除都用贴着选区的气泡

参照 rescript：选中文字 → 浮出小气泡 → **✂ 删除** / **✎ 修正**。

- 删掉了旧的「改文字」输入框。表单是第二个状态（打开 / 取消 / 目标），
  和选区状态容易不同步；旧实现里那个按钮曾把 `undefined` 当提案发出去。
- 气泡**贴在词的下方**而不是上方：词的上一行是句头（时间、说话人、标签），
  气泡盖住它等于盖住用户正在判断的上下文。只有下方放不下时才翻到上方。
- 气泡位置按**中心**做视口钳制（元素是 `translateX(-50%)`）。
  早期按左边缘钳制，靠近右边距时气泡有一半在屏幕外。

### 决策：状态用颜色表达，并且落库

| 状态 | 表现 | 存储 |
|---|---|---|
| 已删除 | 红字 + 删除线 + 淡红底 | `deletion` 行 |
| 部分删除 | 红字 + 点线 + 半格底色 | `deletion` 行（只盖住词的一部分） |
| 已修正 | 蓝字 + 淡蓝底 + 下方蓝线 + ✎ | `token.revised = 1` |

`revised` 放在 token 行上，而不是从 `edit_op` 反推：操作日志按 `idx` 记录，
而文本编辑会重排 `idx`；而且"这个词被人改过"在撤销之后**依然是事实**。

**部分删除必须单独一档**：边界拖动会啃掉词的一边。整词画删除线是在声称
"这段音频没了"，而它其实还有一半能听见——这是会让人不信任工具的谎报。

### 决策：说话人改名只碰一行

`sentence.speaker_id` 存**项目内局部整数**，不是 `speaker.id`。于是：

- 改名 = 改 `speaker` 表一行，所有句子立刻跟着变；
- 模型不做分人时也能用：手动 `POST /speakers` 建一个，再把句子指过去；
- 删除说话人**不清空句子的标注**——那是用户没要求的改写。视图会给孤立的
  `local_id` 合成默认名字，所以 UI 上"删掉"表现为名字恢复成「说话人N」。

实测 `qwen-audio-3.1-asr-flash-filetrans` 对 17.6s 单人样本返回 **0 个 speaker**、
所有 `speaker_id` 为 NULL，所以手动路径不是兜底，是这类音频的唯一路径。

### 顺带修掉的三个真 bug

1. **词级合并迁移可重复执行**：`3c1a7d90e5b2` 的"孤儿检测"用
   `covered = sum(end-start) < len(tokens)`，这个条件**恒为真**（合并必然减少 token 数），
   于是第二次执行把整份稿子又插了一遍：31 → 62 个 token，句子 4 覆盖 `[24,62)`。
   改为按 `src_word_idx` 连续段消费的 `consumed: set[int]`，并加幂等前置检查。
2. **`sentence_count` 从不更新**：转写时写一次，之后任何另起/合并都不改。
   顶栏显示「5 句 · 31 词」里的"5"曾经是"3"。现在 `_persist_spans` 同步写回，
   并加迁移 `9d21c4a7f0be` 重算存量行。
3. **切点吸附会往内挪**：删到 6010ms、静音谷 5991–6100，结果只删到 5991ms，
   19ms 用户删掉的音频回来了。改为**只向外吸附**（起点只左移、终点只右移）。

## 热词真正生效、波形缩放与中文路径（2026-11-06）

这一轮修的是五条用户报的缺陷。前两条看起来是"界面没做"，其实是**数据没到**；
第三条是根因性的；只有第五条纹波是纯交互工作。

### 缺陷 1：中文文件名识别不了

现象是"用中文路径上传失败，改成英文就好了"。听上去像编码校验或文件选择器的问题，
实际是 `subprocess.run(..., text=True)`。

`text=True` 等价于用 **locale 编码**解码子进程输出。这台机器是中文 Windows，
`locale.getpreferredencoding(False)` 是 **cp936**，而 `sys.getfilesystemencoding()`
是 utf-8——两个编码不一致，问题就藏在这个缝里：

1. ffprobe 的 JSON 里会把它读到的**文件名原样回显**；
2. 文件名含中文 → UTF-8 字节 → 用 cp936 解码 → 解码线程抛 `UnicodeDecodeError`；
3. `subprocess.run` 把这个异常**吞掉**，`returncode` 仍是 0，但 `stdout` 变成 `None`；
4. `probe()` 拿到 `None` 去 `json.loads("{}")` → `streams == []` →
   报"文件里没有音轨"。

也就是说：文件是好的，ffprobe 也是成功的，报错信息完全指向错误的方向。
真机脚本 `probe_text_mode.py` 的对照结果：`text=True -> rc 0, stdout is None: True`，
`encoding="utf-8" -> rc 0, streams: 1`。

修法：`media/ffmpeg.py`、`media/render.py`、`media/probe.py` 一律
`capture_output=True, encoding="utf-8", errors="replace", check=False`。
`errors="replace"` 是刻意的：文件名被替换成 `?` 不该成为拒绝这段音频的理由。
`media/peaks.py` 本来就停留在字节模式（`s16le` PCM），不受影响。

回归测试 `tests/test_media_paths.py` 覆盖中文文件名、中文目录名、中文目标路径，
外加一条 **AST 级**的"谁都不许再用 `text=True`"检查——不是字符串匹配，因为那三个
模块的注释里正好写着 `text=True` 这个反面教材，纯 grep 会误伤自己的文档。

### 缺陷 2 & 3：热词从来没被发出去

用户的原话："加了全局热词「漫物质」「马小褂」，依然识别成「漫无日」「马小挂」，
需要排除一下，增加的热词是否在生效？"——**没有生效，一次都没有。**

链路追下来是这样断的：

```
NewProjectDialog  → POST /transcribe { use_hotwords: true }
TranscribeIn      → 没有 use_hotwords 字段 → pydantic 静默丢弃
TranscribeOptions → vocabulary = None
AsrRequest        → vocabulary = {}
_build_body       → parameters 里没有 vocabulary
```

`existing_vocabulary()` 早就在 `services/hotwords.py` 里写好，`routers/hotwords.py`
和 `routers/proofread.py` 都在用，只有**转写这条路没调**。
数据库里 `transcribe_job.params_json` 记的是 `"vocabulary": {}`，是自证。

两处根因，都得修：

1. `TranscribeIn` 加 `use_hotwords: bool = False`；路由里在
   `vocabulary is None and use_hotwords` 时调用
   `hotword_service.effective_vocabulary(...)`，并且**在路由层合并**而不是在
   service 层，因为 job 快照要记录"这次实际发了什么"。
2. 加了 `VersionOut.hotword_count`，把实际条数返回给前端。0 是一个有意义的答案：
   它把"热词关了"和"热词开了但表是空的"区分开，UI 才能说清楚。

验证用 `scripts/verify_hotwords.py`（真后端 + 真百炼 + 真 SQLite）：

```
episode hotwords: 马小褂
vocabulary preview: {"漫物质": 3, "马小褂": 3}
version: hotword_count = 2
params.vocabulary: {"漫物质": 3, "马小褂": 3}
转写文本：「各位听众大家好，欢迎收听本期的漫物质，我是今天的主持马小褂。」
```

同一段音频、同一句话，在热词生效前是"漫无日 / 马小挂"。

### 缺陷 4：热词编辑搬到该在的地方

原来的流程是"先转写完，进了工作台，才有热词面板"——热词是识别的**输入**，
等识别完了再提供编辑入口，等于把唯一有用的时机错过了。勾选框指向一个用户
还没法填的列表，是这个缺陷最直白的表现。

- 抽出 `HotwordEditor`（`apps/web/src/HotwordEditor.tsx`），
  一处实现、三处复用：工作台侧栏、新建项目对话框、设置里。
  三份拷贝迟早会漂移，何况其中一份还要处理"还没有 media_id"的中间态。
- 新建项目对话框：勾上"转写时启用热词"就在下方展开编辑器。
  **本期热词先存本地草稿**——它只能挂到 media_id 上，而 media 要等项目创建后才有；
  提前建项目会在用户取消时留下孤儿项目。所以在 `create()` 里、
  **转写之前**才 `setEpisodeHotwords(...)` 落库，然后才发识别请求。
- 设置菜单拆成两项：「模型与参数…」和「热词与校对…」，打开同一个对话框、
  滚到不同 section（`SettingsSection`）。"热词与校对"里放全局热词、本期热词、
  `use_hotwords`、`use_proofread`、`hotword_weight`、`proofread_chunk_size`。
- 顺带发现一个 API 设计缺陷：`POST /media/{id}/hotwords` 是**整体替换**语义
  （大纲提取需要重建整张表），前端"添加一个词"也复用它，就会把已有的词全删掉。
  界面上表现为"加了第二个嘉宾名，第一个没了"。修法是加两个**窄操作**端点：
  `POST .../hotwords/append` 和 `DELETE .../hotwords/{text}`，
  `addEpisodeHotword` 改打 append。`tests/test_hotwords_episode.py` 用 9 条用例
  把"追加"和"替换"两种语义钉开，其中一条专门测"替换端点仍然是替换"，
  免得后人把它也"修"成追加。

### 缺陷 5：波形滚动与滚轮缩放

波形一直是"整段压到容器宽度"，一小时节目等于一个像素 4 秒，什么都看不出来。

关键决策：**缩放是窗口，不是更宽的画布**。3 小时、64 buckets/s 是 69 万个桶，
8 倍缩放就是 550 万个，浏览器会先被 JSON 噎死，一个像素都画不出来。所以画布宽度
保持容器宽，只画 `[from_ms, to_ms)`——这正是后端 `GET /waveform?from_ms=&to_ms=
&buckets_per_second=` 早就支持的形状，**后端一行没改**。

- 滚轮缩放锚定**指针位置**（`zoomAt`），不是窗口中心。锚在中心的话，
  每滚一格光标下的词就往边上滑，用户得用滚动条追它。
- 滚动条是**自绘滑块**而不是原生 overflow：没有更宽的元素可以滚。
  滑块可拖、轨道可点击翻页、双击回到全览。
- 请求按窗口宽度重算 `buckets_per_second`（`bucketsForWindow`），并做 90ms 防抖；
  不重算的话，放大后波形会变成台阶。滚到底时放行 `deltaY`，页面还能正常滚动。
- 缩放算术抽成 `apps/web/src/waveView.ts` 纯函数，19 条 `node --test` 用例覆盖：
  边界钳制、锚点不动、放大再缩小回到原窗口、"零倍缩放"不除零、

## 一键清理（2026-11-06）

参考 Rescript 的 [One-click cleanup](https://www.getrescript.com/remove-filler-words)，
按它的四条真实教训落地，但把「一点就走」改成「先给清单再执行」。

### 为什么拆成三类，而不是一个大按钮

Rescript 的清理实际是两条独立管线（填充词 + 静音），他们漏了第三条，而第三条
对中文播客是最关键的：**识别会把整个「嗯」吃掉**。Whisper 这样，百炼也这样。
音频里是一段语音，稿子里一个字都没有——纯文本匹配永远找不到它。

所以是本模块的三类：

| 类别 | 依据 | 为什么必须独立 |
|---|---|---|
| 口癖词 `filler` | token 文本对词表 | 用户可能只想删这个，不动静音 |
| 未转写语流 `disfluency` | **语音 − token 覆盖** | 稿子里根本没有这个字，只能从音频摸 |
| 静音 `silence` | 检测器的静音区间 | 有独立的阈值和 padding，语义不同 |

关键实现：**语音 = 静音清单的补集**。不需要引入 VAD，因为我们已经有
`ffmpeg silencedetect`；它的补集就是语音。再减去 token 覆盖，剩下的就是
「有声但没字」的片段。零新依赖。

### 四条从 Rescript 源码学到的规则

1. **不跨词合并切割**（他们 PR #115 "Keep short words between removed silences"
   修的就是这个）。两个 0.4s 静音之间夹一个 60ms 的「对」，朴素合并会把它一起切掉。
   我们更危险：`core/edl.py` 的 `_drop_slivers` 会丢掉 <80ms 的保留岛，
   于是那个「对」从渲染里消失、却还在稿子上显示——用户看不见自己丢了什么。
   规则写在 `_merge_silence_cuts` 里，`test_short_word_between_two_silences_survives`
   专门盯住它。
2. **默认词表刻意保守**。Rescript 明确不收 like / so / right；我们同理不收
   「就是说」「然后呢」「那个」——它们大多数时候是正常用词。`FORBIDDEN_DEFAULTS`
   是**测试里**的断言，不是注释里的劝告。
3. **两侧留 pad**，防止削掉音素；但**媒体首尾切齐**，否则文件开头结尾会留一段空白。
4. **相邻口癖合并成一次切割**。三个「嗯」是 1 处不是 3 处——用户数的是切割次数。

### 决策：先给清单，再执行

Rescript 是一点就走，我们**计划与执行分离**：

```
GET  /versions/{id}/cleanup/plan          → 只读，返回三类清单 + 计数 + 时长
POST /versions/{id}/cleanup {kinds:[...]} → 才真的写 deletion
POST /versions/{id}/cleanup/restore?source=filler|batch=cln_xxx
GET  /versions/{id}/cleanup/counts        → 菜单里「还原口癖词（12）」的数字
```

对话框里每个类别都是可勾选的，显示「3 处 · 840 毫秒」；下面列出**具体切在哪**
（时间、类别、文本、第几句），并可以调阈值重算。`执行清理` 按钮上就写着会删几处。

### 决策：一次清理 = 一条撤销记录

400 条 deletion 不能变成 400 条历史。`deletion.batch_id`（迁移 `4e18c2a9f7b1`）
+ `edit_op.op_type="cleanup"` 的 payload 里存整批 id：

- `undo_op` 现在认两种：`boundary`（恢复快照）和 `cleanup`（把这一批翻回去）；
- 历史面板显示一行「一键清理 / 口癖词 3 · 未转写语流 1」，`undoable: true`；
- 另有按类别的还原入口（`restore?source=`），因为连续清理三次之后，
  用户想要的是「把口癖都还回来」，不是按时间顺序撤销三次。

### 决策：改设置不追溯已应用的切割

这条写进了测试（`test_changing_the_threshold_does_not_alter_applied_cuts`、
`test_removing_a_word_from_the_filler_list_does_not_restore_it`）。
理由很直接：如果阈值联动，用户把 0.3s 改成 0.5s、点保存，就等于**在没有提示的情况下
又删了一轮音频**。设置只喂下一次计划，已应用的切割是历史事实。

### 静音清单缓存（`media/silences.py`）

清理需要**全片**静音清单，而 `build_edl` 每次编辑都会重算——3 小时节目会卡死。
所以照抄 `media/peaks.py` 的形状：`{media_sha}.v1-{noise}db-{min}s.json`，
key 里带**检测器参数**（改阈值必须换 key，否则用户调了滑块却看不到变化）。
真实数据：75 秒音频首次检测 0.22s，命中缓存后 0.012s。

顺带把**检测器参数**和**切割阈值**分开了：
`silence_noise_db` / `silence_min_duration_ms` 决定「哪里算静音」，
`cleanup_min_silence_ms` 决定「多长才值得切」。两者混用会让「吸附切点」
跟着清理阈值一起变，是个隐蔽的耦合。

### 修掉的两个真 bug

1. **设置对话框每渲染一次就重新拉一次 `/api/settings`**。`refreshHotwords` 是
   `useCallback`，但它的依赖链走到一个父组件内联构造的 prop，identity 每次都变；
   把它放进 effect 依赖里，effect 就跟着重跑。后果极其阴险：
   **用户输入几百毫秒后，输入框被服务端的旧值覆盖**——看起来像「设置保存不上」。
   修法是把最新回调放进 `useRef`，effect 只依赖 `open`。这个 bug 在加口癖词表
   （一个长 textarea）之前一直没被发现，因为短输入通常来不及被冲掉。
2. **迁移不是幂等的**：`4e18c2a9f7b1` 第一次写没有 `PRAGMA table_info` 前置检查，
   `test_running_the_migration_twice_does_not_duplicate_tokens` 立刻炸在
   `duplicate column name: batch_id`。加 `_has_column` 守卫后通过——这条测试
   模拟的正是「部署失败后重放」，是真实场景。

## 保存即下载、大纲导入热词、缩放不再被编辑重置（2026-11-06）

用户报的三条，都不是「坏掉了」，而是「做完之后不知道自己做了什么」。

### 1. 点保存项目没有下载，也不知道文件在哪

两个独立缺陷叠在一起，缺一个都解释不通用户的观察：

- 存档写在 `data/projects/<id>/<项目名>.project`，`_to_out` 回的是**相对路径**。
  这个路径只对「站在仓库根目录的人」有意义，「载入项目」从任何别的地方粘进去都失败。
- `run()` 在动作**返回之后**写 `「label」完成`，把动作自己刚写的「已保存到 …」
  覆盖掉了。所以提示是真的出现过，随即被抹掉——用户看到的是「完成」两个字。

修法分三层：

1. 后端 `_to_out` 一律 `path.resolve()`。
2. 前端 `run()` 记一个 `noticeClaimed`，动作自己 `say()` 过的就不再覆盖。
3. **真的要下载**：`GET /archive/file` 已经在，但它只回文件；而
   `POST /archive` 只回元数据。用户要么下载、要么知道路径，二选一。
   现在下载响应的 header 里带上服务端绝对路径（`X-Archive-Path` 等），
   前端 `fetch` 一次拿到 blob + 路径，再把 blob 交给浏览器。

> header 必须百分号编码：HTTP header 是 latin-1，项目名「第 07 期」直接塞进去
> 会在响应阶段抛异常。测试 `test_download_headers_survive_a_chinese_project_name` 盯这个。

「载入项目」对话框现在预填上一次保存的路径——保存完想立刻载回来验证，不用复制粘贴。

### 2. 新建项目时不能从大纲导入热词

大纲抽词端点原来挂在 `/projects/{pid}/media/{mid}/hotwords/suggest` 上。
可是**大纲导入唯一有意义的时刻，是转写之前**，那时项目还不存在——端点把功能
挡在了它唯一有用的地方之外。

补了无状态版 `POST /api/hotwords/suggest`（不需要 project、不需要 media、不落库），
前端 `OutlineImport` 组件：

- 粘贴大纲 → 「提取候选」→ 得到带权重的词条；
- **候选默认全选，但可以逐个取消**——LLM 会给出几个看起来很像的错词，
  而每个错词都会让识别偏向它（§6.1），所以必须先过一遍人工；
- 「加入本期热词（N）」只把勾选的并入草稿；已有词标「已有」并划线，不重复加；
- 权重保留抽取器的排序（标题词 > 一次性提及），不压成默认 3。

草稿在 media 行存在之前只存在于内存，创建时按顺序落库：建项目 → 注册音频 →
写热词 → 写大纲 → 转写。顺序是硬要求：热词必须在转写**之前**进库，否则这一轮
转写根本用不上它们。

### 3. 拖句子边界会重置波形缩放

根因不在 `Waveform`：拖边界提交编辑 → 编辑调 `onReload()` → `load()` 里
`setLoading(true)` → 渲染分支 `if (loading) return "加载中…"` → **整个 `<Desk>` 连同
`Waveform` 被卸载**，组件内 `useState` 的 `view` 自然回到「全片」。

对照 Rescript：它的 zoom 也是组件内 `useState(1)`，从不重置，因为编辑**不会重挂载**
编辑器。所以正确修法是让重载不卸载工作台，而不是往波形里塞持久化。

两处都做了：

- `App` 用 `bootRef` 区分「首次加载」与「编辑后重载」，只有前者清屏；
  渲染门改成 `if (loading && !boot)`。
- `Waveform` 另加一层按 media 的记忆（`VIEW_MEMORY`），覆盖项目切换、HMR 这类
  真的重挂载；全片视图不入表（那是默认值，记住只是噪音）。
  恢复时走 `initialView()` 做 `clampView`——重新导入的音频可能更短，
  直接还原一个 40 分钟开头的窗口会画出空白画布，且没有任何提示。

### 顺带修掉的一个真 bug（工作台的大纲提取）

`generateFromOutline` 调完 `suggest` 就刷新列表，然后报「从大纲提取了 N 个热词」。
但 `suggest` 只**提议**，不写库——真正的写入要调 `suggest/accept`。结果是：
提示说有 N 个词，chip 区还是空的，下一次转写一个热词都没带上。
现在按 `suggest → 人工确认 → accept` 走完。CDP 脚本 `check-workbench-outline.mjs`

## 时间轴对齐（2026-11-09）

用户报告：点「播放这句」时第一个字被吞掉一半，有些句子完全听不到第一个字。

### 诊断：偏差来自百炼，不是我们的链路

逐段验证，每一条都可复现：

| 环节 | 验法 | 结果 |
|---|---|---|
| ffmpeg 转码（原始 → 16k 单声道 mp3） | 两版都解成 PCM 做互相关 | 平移 **0 样本** |
| 入库（ASR JSON → token 表） | 8246 个词逐个比对时间 | **0 处不一致**（6 个空词被丢弃，其余原样） |
| 浏览器播放 | 页面内 `decodeAudioData` 后重测 | 与 Python 一致，−98 ms 两边都对上 |
| MP3 编码延迟（576+529 样本 = 69 ms） | 同一段 60 s，mp3 与 wav 各识别一次 | **差 0 ms**（中位数 +0，最大 ±20），模型做了 gapless 补偿 |

实测口径：两个真实项目、997 个「前面确有 ≥250 ms 停顿」的句首词，声学起声减去模型 `begin_time`：

    中位数 −65 ms   平均 −86 ms   p25 −125   p75 −35
    |偏差| ≤ 40 ms 的句子只占 31 %
    偏晚 > 100 ms 占 27 %

句中词同样偏晚（中位数 −60 ms，n=1691）。所以是**整条时间轴**偏晚，不是只有句首。

**为什么不用逐词校正**：模型时间戳粒度是 10 ms（末位全是 0），单句误差不可从音频稳定复现；能量法在连读里分不清词界。一个常数才是这类系统性偏差的正解。

### 决策：API 收「目标值」而不是「步长」

`POST /api/versions/{id}/time-shift {shift_ms: -80}` 的含义是「让这条时间轴相对模型原始时间偏 −80」，服务端施加的是 `target - current`。后果有两个，都是想要的：

- 同一个请求点两次不会变成 −160，面板上的「撤销」就是「对齐到 0」，用户不需要知道自己点过几次；
- 只有**差值**被施加，所以用户手动拖过的边界保留相对位置。若从 `transcripts/*.raw.json` 全量重算，那些拖动会被静默抹掉（`edit_op` 里有 36 条 `boundary_time`）。

`transcript_version.time_shift_ms` 只是**记录**：token / deletion 行里已经是平移后的时间。没有这一列的话，「当前偏移多少」不可观测——而「再减 80」不是一个值，是对施放过几次的猜测。

### 决策：夹紧差值，不夹紧行

要求 −1000 ms 而首个词在 240 ms 时，服务端把**差值**降到位移后最早时间仍 ≥ 0，并回 `clamped: true` 与原因。逐行夹会让录音开头被压扁、改变内部相对时序；夹差值保证整条轴刚性。同理上界按 `duration_ms`。

### 决策：token 与 deletion 一起移

删除区间挂在词边界上。只移 token 会让每个剪切点滑到相邻音素——音频剪错位置，而且用户听不出来为什么。520 行 deletion 一起平移。

### 面板：立即生效，不用「保存」

其余六个面板都是「下次生效」的偏好，改完按保存。这个面板改的是已经存在的转写，所以按钮按下就写库，底栏直接写「对齐立即生效，与本面板的「保存」无关」，并把「保存」按钮换成「关闭」。一个按钮两种提交语义，是用户按了取消却发现时间轴已经变了的经典成因。

导航里排在最后，摘要写明「直接改写当前版本」（其余六项都是「下次生效」）。

**自动对齐**（逐句用波形能量定位）放面板里但按钮置灰，实际实现记在仓库根 `todolist.md`：它要处理人工拖过的边界、删除区间映射、渲染切点和「撤销回到基线」四件事，不是加一个函数。

## ShowNotes 提示词按手写稿重做（2026-11-09）

**症状**：自动生成的 ShowNotes 是一份播客**总结**，不是一份让人想点开的文案。
三个具体表现：H1 是项目名（「播客-费那奇MV」）；summary 是 60–120 字的一句话，
读完就没有悬念了；中间还有一块「本期要点」6 条 bullet —— 读者看完要点，
播放按钮就没有必要点了。时间轴是 `01:10` 两位格式，和发布平台上其他节目的
`00:01:10` 排不成一列。

**对照目标**：`samples/播客-费那奇MV_ShowNotes_final.md`（手写）。结构是
H1 = 一个观点型标题 + 两段散文（第一段讲这件事为什么值得聊，第二段介绍
嘉宾和作品，以「欢迎大家收听」收口）+ 8 条 `- **00:01:10** 标题`。没有要点列表。

**怎么改**（`core/script.py`）：

| 改动 | 之前 | 之后 |
|---|---|---|
| 标题 | 无，H1 用项目名 | `titles` 5 个备选，`fit_titles` 按 22 字筛，H1 用第一个 |
| Summary | 一句话 60–120 字 | 两段 200–240 字，第二段以邀请收听收口 |
| 要点 | `points` 4–6 条 | **删掉**，`ShownotesPlan` 里没有这个字段 |
| 时间码 | `MM:SS`（有小时才带小时） | `HH:MM:SS`，小时位永远打印 |

**标题计数**：`count_title_chars` 汉字 / 全角标点 / 半角字母数字各记 1
（"MV" 记 2）。超长的**丢掉而不是截断**——截断会砍掉双段式标题的后半段，
读起来还是中文，但已经不表达原来的意思了。前端 `titleCount.ts` 是同一套算法，
两处不一致比不显示更糟。

**主持人识别**：手写稿的 8 个章节点实测有 6 个正好落在主持人的发言上
（马小褂：「感谢AA关于就是小广这部MV的分享」这类接话）。所以「一个章节 =
主持人重新接过话头的地方」是能从数据里复现的规则，前提是知道谁是主持人。
`host_speaker` 用三条判据：开场 8 轮内的自我介绍最硬（「欢迎收听」「我是今天的
主持」）；其次提问率（实测主持人 13 % 的轮次以问号结尾，嘉宾 6 %）；最后谁先开口。
**不用「谁说话最多」**——同一期实测 128 : 126 轮，这个指标量的是语速不是角色。

**章节吸附**：模型给的 `line` 反查 `turns[index].start_ms`（时间戳只从转写稿读），
然后再**对称**吸附到 12 秒内最近的主持人轮次。第一版只往后找，真机输出里
「00:50:31 互联网美学命名权」锚在嘉宾的「嗯。」上，主持人 0.1 秒后才开口——
只往后找会修好一半、静默留下另一半。

**三道机械校验**（都只 warn，不拒绝）：`unverified_numbers` 把概述里
转写稿找不到的数字列出来（实测模型把「今年入围费那奇」升级成「2023 年入围」，
具体、通顺、错的）；章节覆盖率低于 75 % 时提示可能漏了转折点（3 小时节目
只到 50:31 是真实发生过的一次）；概述超过 300 字提示超长（上限 260，实测写到 405）。

**文件名**：`_filename` 改用 `filename_base`（项目名），不再用 H1。H1 是模型写的，
每跑一次都不一样，否则同一期会在文件夹里留下两个名字。

**验证**：真机 3 小时节目跑 6 轮。最终输出 11 章覆盖到 01:00:13（结语），
10/11 落在主持人开口处；标题 5 个全部 ≤ 22 字；概述两段 220 字。
680 后端用例（+29）、139 前端用例（+6）、`ruff` / `mypy --strict` / `tsc` /
`vite build` 全绿。

## 字幕区三件事：隐去、快捷键、多词修正（2026-11-09）

**要的是什么**：口水词要能从字幕里去掉，但**不能剪音频**——剪了会在句子里留一个
可听见的空洞。原来的两个操作都做不到：`deletion` 同时删音频和文字，`revised` 改文字
但保留它。

| 改动 | 之前 | 之后 |
|---|---|---|
| 隐去 | 无 | `token.hidden`，音频、时间、编号全不动，只从字幕/文稿里跳过 |
| 快捷键 | 无 | `Del` 删除 / `Enter` 修正 / `Backspace` 隐去 |
| 多词修正 | 禁用（"一次只能修正一个词"） | 拖选 N 个词合并成 1 个，外边界不变 |

**为什么隐去不做成「带标记的 deletion」**：`deletion` 行进 EDL，进 EDL 的东西最终会
到渲染器。单独的布尔字段从结构上就不可能漏进音频路径——这不是靠代码自律，是靠
数据流。测试 `test_hiding_does_not_move_any_timestamp` 和
`test_subtitle_text_omits_hidden_words_but_keeps_the_timing` 守住这两点。

**为什么修正会取消隐去**：改写一个词是"这个字应该说成什么"的决定，改完还藏着
等于把这个决定丢了。

**多词修正暴露的一个真 bug**：第一次在真实转写稿上合并 3 个词，服务端 500，
`UNIQUE constraint failed: token.version_id, token.idx`。根因是重排编号的写法：
收缩 3 个 token 时第 5 行想拿第 2 行的编号，而第 2 行还在；旧实现"从后往前逐个改"
只在恰好按这个顺序发 UPDATE 时才对，而顺序不由这段代码控制。改成**两段式**：
先把整个尾部挪到所有存活编号之上（`+1_000_000`），再落回最终位置，两步都与顺序无关。
`test_multi_word_correction_renumbers_without_colliding` 复现了这个场景。

**另一个真 bug（迁移）**：加 `token.hidden` 之后，`test_running_the_migration_twice_
does_not_duplicate_tokens` 开始报 `CircularDependencyError`。原因是
`batch_alter_table` 从**当前** schema 重建表——重放 `7b4f2c9a1d63`（加 `revised`）时
那一列已经在表里了，于是列排序的 pair list 出现环。修法：两个迁移都加
`PRAGMA table_info` 幂等守卫，和 `4e18c2a9f7b1_deletion_batch_id` 一直以来的写法一致。
`7b4f2c9a1d63` 之前只是**侥幸**能重放，这个测试补上了「重放后表结构不变」的断言。

**顺手修的**：句首 meta 区的标签没有 gap，`已修改` 和 `已隐去 1` 挤成
`已修改已隐去 1`，读起来像一个长标签。

**验证**：真机走查四项——气泡三个按钮都在且标题带快捷键；三个键都真的触发对应操作
（`afterBackspace.hidden` 多了刚选中的词，`afterDelete.cut` 有了刚删的词）；
Shift+点选 3 个词后 Enter，输入框预填「小广她」，提交「送別」后变成一个词且后续
文本不前移。700 后端用例（+21）、136 前端用例、ruff / mypy --strict / tsc /
vite build 全绿。

**走查污染了真实项目，已还原**：走查会真的改 `data/app.db`。删掉的删除区间已恢复、
6 个 hidden 标记已清除、3→1 的文本合并已用项目存档
（`data/projects/prj_1m6v2m8anfpyqq3w8qt/播客-费那奇MV.project`）恢复——逐 token
比对文本差异为 0，13 条走查产生的 `edit_op` 已删除。以后的走查脚本应该跑在临时
项目上，或者写明「会修改真实数据」。

## 隐去的词在波形上画一条灰线（2026-11-09）

**要的是什么**：隐去只影响字幕，波形上看不出任何痕迹——用户问「我刚才到底改了什么」
时，唯一线索是句首那个「已隐去 N」的标签，而那个标签在他正在看的时间轴上根本没有。

现在：每个隐去区间的**起点**画一条 1px 竖线。

**为什么是线而不是块。** 删除已经是红色块了。块在说「这段音频没了」，而隐去恰恰
相反：音频还在，只是字幕里没有。形状必须不同，否则用户会以为剪掉了东西——这正是
一轮之前把隐去做成独立布尔字段而不是「带标记的删除」的同一个理由，在视觉上的延续。

**两个真问题，都是实测发现的：**

**① 颜色。** 第一版用 `rgba(100,116,139,0.55)`（和句边界线同色系）。实测发现它和
波形柱 `#475569` 只差 7 个亮度级，在最需要看见的地方（波形上）完全消失。换成近白
的浅灰后，在波形上清楚了，但在词间近白的空隙里又消失了。最终：**白描边 + 灰芯**
（先画 3px 半透明白，再画 1px 灰），两种背景上都读得出，而且仍然是一条细线。

**② 合并判据。** 第一版按「时间相接」合并连续隐去的词。真实转写稿里词与词之间有
100–200ms 静音，所以选中 7 个连续的词、点一次隐去，画出来是**两条线**（第一条线的
结束和第二条线的开始之间隔着静音）。改成按 **token 流相邻**判定：中间没有未隐去的
token 就是一段。

**第三个问题（顺序）**：一开始画在句子带那一层（波形之前），结果波形柱把线盖住，
只在峰的间隙里露出来，看着像噪点。挪到波形之后、句边界手柄之前。

**实现**：`transcript.hiddenSpans(tokens)` 把 token 流折成区间（纯函数，5 个单测覆盖：
只挑 hidden、相邻合并、跨静音合并、中间夹着可听词不合并、零长度跳过）。
`App.tsx` 算一次传给 `Waveform`，`Waveform` 在 draw 里画。legend 加了一句
「灰色竖线是已隐去（音频还在）」。

**验证**：真机走查用「开/关对比」而不是猜颜色——同一缩放、同一批滚轮事件，隐去前后
各截一次，逐像素差分。关时 `lineHits: []`，开时 `lineHits: [284]`（一处连续区间
一条线，而不是两条）。放大截图确认线在波形柱上仍可辨。

**走查又改了真实项目，已还原**：这轮走查在「播客-费那奇MV」上隐去了十几个词。跑之
前用 `sqlite3.backup()` 存了 `.tmp/app.db.before-wave-walkthrough`，跑完整体还原，
确认 hidden=0、token 数 8235、最新 op 回到用户自己的 `text`。**以后这类走查一律先
备份再跑**——比事后逐条撤销可靠得多（上一轮就是因为逐条撤销撞上「只能撤销最近一次
操作」的限制，最后靠项目存档才恢复）。

## 隐去在波形上改成灰色斜线区域（2026-11-09）

**要的是什么**：上一版只在隐去区间的**起点**画一条灰线，两个毛病——太细、看不见；
而且只知道从哪开始，不知道到哪结束。

改成**区域**：浅灰底 + 45° 斜线 + 左右两条边线，覆盖整个画布高度。

**为什么还是不能像删除那样。** 删除是实心红块、没有任何纹样，因为音频真的没了。
隐去是浅色洗淡 + 斜线，斜线读作「从文字里划掉」，下面的波形仍然透得出来——这正是
事实：音频还在。形状必须不同，否则用户会以为剪掉了东西。

**斜线间距是调出来的，不是随手写的。** 一开始 7px，中等缩放下看着还行；但放大到
「一段隐去只有两三个词」（10–30px 宽）时，有的区域一条斜线都没捕到，看起来就是个
纯灰块——又变回"像删除"了。收到 6px 并加深颜色（`rgba(71,85,105,0.32)`）之后，
任何宽度的区域至少能捕到两三条斜线。

**边线用 1 设备像素而不是 1 CSS 像素。** dpr=1.5 时 1 CSS 像素等于 1.5 设备像素，
两边各摊一半抗锯齿，放大看是一条发虚的灰带而不是边。

**区域最小宽度 2px。** 全览下（61.6 分钟铺满 978px）一个 200ms 的词是 0.05px，
不兜底就完全不可见。

**验证**：走查用**开/关差分**——同一缩放、同一批滚轮事件，隐去前后各截一次画布位图
逐像素比对。放大视图下开时有两段连续列区间（`282..418`、`528..595`，各覆盖 251/252
行，即整高），关时为空。全览下 13 处隐去只占 10 列（`runs: [(3,4),(14,15),(41,41),
(57,58),(93,95)]`），没有糊成一片。

判据踩过一个坑：一开始按颜色找"浅灰"，全部落空。原因是画布先 `clearRect`，区域填充
是 `rgba(148,163,184,0.22)` 直接落在**透明**像素上（147,167,186,**alpha=26**），和页面
白底合成后才变浅灰。读 `getImageData` 拿到的是未合成的值。

**走查污染**：这轮在真实项目上隐去/恢复了十几轮，跑前用 `sqlite3.backup()` 存了
`.tmp/app.db.before-hatch`，跑完整体还原（hidden=0、token 8235、最新 op 仍是用户
自己的 `text`）。

## 波形缩放只剩两个入口（2026-11-09）

**用户报的问题**：拉动时间轴时误点滚动条、或连点进度条的第二下落到滚动条上，缩放就
重置成「全部」。频繁重置让操作非常不顺畅。

**根因**：自绘滚动条上挂着 `onDoubleClick={() => onZoomTo({from: 0, to: total})}`。
「连点进度条」的第二次点击正好落在下面那条滚动条上，浏览器把它合成 `dblclick`——一次
误触就把花很久调出来的窗口扔了。

**改法**：把重置能力从滚动条上**整个拿掉**，而不只是加个判断。

| 入口 | 之前 | 现在 |
|---|---|---|
| 波形上滚轮 | 缩放 | 缩放（保留） |
| − / + / 全部 按钮 | 缩放 / 重置 | 缩放 / 重置（保留） |
| 滚动条双击 | **重置到全览** | **删除** |
| 滚动条拖滑块 / 点轨道 | 平移 | 平移（保留，只改 `from`） |
| 画布聚焦后 `+` `-` `0` 键 | 缩放 / 重置 | **删除** |
| 画布聚焦后 `Home` `End` | 平移 | 平移（保留） |

`+`/`-`/`0` 一起拿掉的理由：画布本来就是 `tabIndex=0`（它要响应方向键），聚焦之后
一个误按的数字键就改掉窗口，而画布离鼠标正在操作的地方很远。滚轮和按钮都是**显式
目标**，不可能误触。

**顺带修的同病根问题**：`durationMs` 变化时那条 effect 会重新 `initialView(...)`，
而它读记忆条目或回退全览——重新转写、换一个长度略有不同的媒体文件都会静默清掉缩放。
改成：同一个 `projectId:mediaId` 内只 `clampView`，**只有真的换了媒体文件才重置**。
注释里那句"编编辑边界不该动缩放"是对的，但实现只在 token 编辑时成立，duration 变一次
就破了。

**验证**（`scripts/check-waveform-zoom-entries.mjs`）：放大到 16.1 分钟后在滚动条上
真发两次 click + 一次 dblclick，读数仍是 16.1 分钟；点轨道空白处只移动滑块位置
（`thumbLeft` 0% → 21.9%）跨度不变；按 `0` `+` `-` 三次读数都不动；最后点「全部」
才回到 61.6 分钟。四项断言全过。

`scripts/check-waveform-buttons.mjs` 另外确认滚轮和「+」按钮仍然有效：
61.6 → 16.1 → 12.9 分钟。

**文档**：`docs/frontend.md` §7.1 加了这条约束和它的来历，避免以后有人"顺手"把双击
重置加回去。

## 批量处理：删除与隐去（2026-11-09）

**要的是什么**：一期节目里「嗯」有上百个，一个个按 Backspace 不现实；而删掉这些词
的音频又会在句子中间留洞。所以需要批量地「只从字幕里去掉」。

**最后的结构**不是按「一键删除 / 一键隐去」分，而是按**因素类型**分：

| 菜单条目 | 作用 |
|---|---|
| 删除口癖词… | 剪掉音频 |
| 隐去口癖词… | 只改字幕，音频不动 |
| 删除静音… | 剪掉死气 |
| 删除未转写语流… | 剪掉没有字的语音 |
| 删除全部三类… | 三类一次清掉 |

互斥的只有口癖词那一对。静音和未转写语流**音频里没有对应的字**，隐去对它们无意义，
所以在「隐去口癖词」弹窗里置灰并写明原因「没有对应的字，无法隐去」——整行消失会让
用户以为菜单变了。

**动作在菜单里选，弹窗不再有模式切换。** 中途试过「一个一键清理 + 弹窗内删除/隐去
切换」，那是典型糟糕设计：同一个按钮根据一个用户忘了自己设过的开关做两件截然不同的事。
现在标题就写着这个动作是什么。

**还原拆成两条**：还原已删除口癖词（拿回音频）/ 还原已隐去口癖词（拿回文字）。
合成一条「还原口癖词」用户就不知道自己这一点拿回什么，而且只能拿回一半。

**实现上新增 `token.hide_source`**（`''` = 手动，`'filler'` = 批量）。「还原已隐去」
只认批量的。手动隐去是用户逐字读出来的决定，一次批量还原抹掉它就是覆盖用户的选择。
比把索引记进 `edit_op` 可靠：`idx` 会随多词合并往后挪，记下的索引就指向别的词了。

批量隐去写的是 `hide` 类型 op，**不是 `cleanup`**——后者的撤销实现是"把 deletion 行
标记为已还原"，用它撤销会静默什么都不做。

**`find_filler_cuts` 现在跳过已隐去的 token。** 一个字要么被删、要么被隐；不跳过的话
「删除口癖词」会提议剪掉用户刚决定保留的音频。

**走查发现的一个真问题**：首次打开弹窗要跑静音检测（3 小时素材几秒到十几秒），
这段等待里三类都显示「0 处」。那不是「未知」，用户读到的是「没东西可做」，会直接关窗。
改成计划未到时显示「正在计算…」。

**走查发现的第二个真问题：两个数对不上。** `hide_fillers` 报的是 token 数（183），
而弹窗计的是「处」（173，相邻口癖词合并成一条灰带）。于是确认里写「已隐去 173 处」，
紧接着菜单写「还原已隐去口癖词（183）」——同一次点击两个数，读起来就是 bug。
现在两边都用同一个按 token 连续性分组的函数，测试里钉住它们相等。

**第三个：还原提示被盖掉。** 四条「还原…」用的是 `setNotice` 而不是 `say`，
于是「已还原 183 处已隐去口癖词」过一会儿就被 `run` 的「… 完成」覆盖了。
这正是 `say` 上面那段注释描述的 bug，我又绕了回去。

## 字幕气泡：删 ↔ 还、隐 ↔ 显（2026-11-10）

**两件事，都是同一个产品事实的两个面**：删和隐互斥。一个词的音频要么被剪掉，要么还在。

**第一件：选区已删除时，「隐」必须灰掉。** 对着一堆已经删掉的词点「隐」，会造出一个
下面没有音频的隐去词——一个语义上不存在的状态。反过来也一样：对着已隐去的词点「删」，
剪的是用户刚刚明确决定要保留的声音。所以两个按钮互相看对方的状态。

判定分两层，因为这其实是两个问题：

- **标签**看「全部」：选区全删了，首按钮才变「还」；只要还有没删的，它就还是「删」。
- **能否点击**看「任意」：选区里有一个词已删除，「隐」就已经是假话了。

**第二件：删 变 还，绿色。** 用户的原话是「点击已删除文字『删』按钮也应该变成『还』」。
单字沿用气泡的规矩（删 / 修 / 隐 / 还 / 显），`aria-label` 仍是两个字。

绿色不只是「区分」：这两个按钮占**同一个位置**（一个词要么被删要么没有），所以颜色说的
是「这个按钮往哪个方向走」，不是「这是两个按钮里的哪一个」。还原如果也是红的，读起来像
又一次删除。

**实现上的两个决定：**

- 判定逻辑放进 `transcript.ts` 的 `selectionState()`，不写在 JSX 里——它能被 `node --test`
  直接跑（新增 8 条用例），而写在组件里只能靠眼睛。
- 新增 `POST /deletions/restore`，**按词**还原。不能复用 `DELETE /deletions/{id}`：一条
  deletion 行往往覆盖整句十几个词（`add_token_deletion` 特意把连续词合并成一行，就是
  为了少几个 filtergraph 分支），点一个词就删掉整行，会把用户没指的音频也拿回来。
  行覆盖多个词时，它被标记为已还原，剩下的词按连续段写成新行——一次收窄，历史里就是
  「一条被撤回、一条仍生效」，这正是真相。

**快捷键跟着按钮走。** `Del` 在已删除的选区上是还原，`Backspace` 在已删除的选区上
什么都不做。按键和按钮不一致，肌肉记忆就会走到一条按钮不允许的路上。

**验证**：711→720 后端用例（新增 `test_restore_words.py` 9 条），142→150 前端用例，
ruff / mypy --strict / tsc / vite build 全绿。真机走查五个状态全部符合：初始 删(红)/修/隐、
删除后 还(绿, rgb(21,128,61))/修/隐(灰)、还原后回到初始、隐去后 删(灰)/修/显、显之后回到初始。
API 实测：删 token 3–5，再还原 4，剩下的确实是 (5620,6100) 和 (6500,6820) 两段。

## 03:35.180 点了播放没反应：修法与取证（2026-11-10）

**症状**：点那句的 ▶，传输栏变成「暂停」，一点声音都没有，也没有任何报错。

**根因是三件事叠在一起**，单独看每一件都不像 bug：

1. **Chrome 的 MP3 解码器在这个位置有一个约 30ms 的坏窗口。** 实测：215.14s、215.20s
   都能正常 seek，215.16–215.19s 报 `MEDIA_ERR_DECODE(3)`。文件本身没问题——`ffmpeg`
   全片 153,998 帧零错误，重新封装也不移动坏窗口，帧头全部合法。是浏览器对某一段
   granule 挑剔。
2. **元素一旦进入 error 状态就不会自己恢复。** 把 `currentTime` 挪到别处完全无声无息，
   `load()` 回原位仍然失败，`load()` 后换一个位置才行。这三条都是实测的。
3. **`void audio.play()` 吞掉了 reject**，所以失败完全看不见。

**为什么之前的走查没抓到**：偶发点位的失败只在特定时间戳出现，而之前的走查只点开头几
句。用 JS 的 `element.click()` 也复现不了——合成点击没有 user activation，`play()`
必然 NotAllowedError，把真正的 decode 错误盖住了。必须用 CDP 的真实鼠标事件。

**修法**：所有播放入口（`play` / `playRange`）走同一个 `startAt()`，按 30 / 60 / 120 /
240 / 400ms 阶梯重试，每次**先 `load()` 再定位**（顺序反了没用）。成功后提示
「这个位置开头的几十毫秒无法解码，已跳过。」；阶梯走完才报错，并建议换一句或导出后试听。
400ms 是上限——再往后就开始吃掉用户想听的那个字。

**一个容易写错的地方**：判断「是不是解码失败」不能看 `play()` 的 reject。坏位下这个
promise **永远不 settle**（实测 4.5s 既没 resolve 也没 reject），所以 `attemptPlay()`
把 promise 与元素的 `error` 事件、600ms 计时器一起 race，然后读 `audio.error.code`。
第一版就是因为死等 promise 而完全没触发重试。

**验证**：真机走查，点 03:35.180 的 ▶ → 日志显示 `seek 215.18` → `play` 被 AbortError
拒 → `load()` → `seek 215.21` → `play ok` → `currentTime` 从 215.18 一路走到 217.97，
`error=null`，提示条写「这个位置开头的几十毫秒无法解码，已跳过。」。前端用例 150→157
（新增 `playbackRecovery.test.mjs` 7 条，钉住阶梯的算术与「必须往前、必须有尽头」）。
ruff / mypy --strict / tsc / vite build 全绿。
## 最后一句的句尾拖不动（2026-11-10）

**症状**：1:01:32.659 那句的句尾边界在波形上拖不动，句首正常。

**根因**在 `core/realign.py` 的 `end` 分支：没有后邻 token 时，上界取的是
`max(low, token.end_ms)` —— **就是它自己的当前值**。于是最后一句的句尾只能往**前**拖，
往后拖一律被夹回原位，而且理由写成「不能晚于 3693570ms（会与相邻字重叠）」，
把原因归给了并不存在的相邻字。句首分支的上界是 `token.end_ms - MIN_TOKEN_MS`，
跟后面有没有字无关，所以句首一直好用——这正是「只有句尾坏」的来源。

讽刺的是，句尾被切掉半个字恰恰是最需要往后拖的场景，而它是唯一拖不动的方向。

**修法**：`adjust_token_edge` 新增 `duration_ms` 参数；缺后邻时上界改为文件时长，
`services/editing.py` 传 `version.duration_ms`。越界理由改为「不能晚于文件结尾 Nms」，
不再甩锅给不存在的邻居（`clamp_edge` 因此多了 `above_reason`）。默认 `None` 表示
「调用方不知道时长」，此时前向不设界——猜一个界比不设界更糟，猜错了会静默截断用户的拖动。

**验证**：真机，点最后一句 → 波形跟到 1:01:32 → 放大 → 从右往左扫到 `ew-resize` →

   对象变成整句，而点时间轴只是「这是哪儿」，把它静默升级成整句操作是越权；
4. 点时间轴 → 字幕区对应的词高亮。

**跳转一律不改缩放。** 缩放是用户一次设定、期望一直保持的状态（§7.1 那条入口纪律），
定位动作顺手改跨度，下一次点击就落到别处了。

**句跳转走 `audibleStart` 而不是 `start_ms`。** 句子开头的词被删掉后，它听得见的起点是
第一个幸存词。Ctrl 取消勾选时不跳——撤回不是定位。

**点时间轴时词是「有就选、没有就清空」。** 词间有 100–200ms 静音，落在那里就别选：
挑最近的词会让「删除选中」删掉用户没指过的音频。查找用 `seek()` 的**返回值**而不是点击
位置，因为 `seek` 会从删除区间里往前snap。

### 做的过程里挖出两个真 bug

**① 全览下点波形什么都不发生。** 走查第一条就卡住：横向六个位置各点一次，时钟一次都
没动。根因不在新代码——`handleAt` 是「6px 内最近的手柄」，而这期 61 分钟 / 1682 句 =
**3364 条边界铺在 978px 上，平均 0.29px 一条**，于是画布上每个像素都在某个手柄的 6px
半径里，点击全被拖拽分支吃掉，按住松手没动就什么都没发生。同一条水平线上点顶部字幕条
（另一条代码路径）立刻跳 38:08，所以一眼能确认是命中判定而不是 seek。

修法 `hitEdge()`：最近的那条要在半径内，**且**下一条不同的边要在半径外，否则返回
「没有手柄」，点击落回去当 seek。两条边在同一像素算同一条（句尾与下一句句首本来就
重合）。第一版比较的是距离排名，而两条相距 4px 的手柄在中点上距离相同、排名差为 0，
会被误判成同一条边放行——改成拿最近那条的**坐标**去比。

**② 气泡飘了 104px。** 点词之后 seek → 播放头跨句 → 跟随效果滚动，而气泡锚点是点击
那一刻的屏幕坐标，不会跟着走。实测（`scripts/check-bubble-anchor.mjs`）：滚 23px 偏
26px，滚 121px 偏 **104px**，长得能压到「操作记录」面板上。修法是在 layout 阶段重测
`[data-token]` 的矩形，而不是算「列表滚了多少气泡挪多少」——行会被重新折行、被虚拟窗口
卸载再挂载，只有元素自己知道它在哪。

### 顺带

- `usePlayback.seek` 现在返回**实际落点**（毫秒）。此前返回 `void`，调用方无从知道
  snap 之后停在哪，只能拿请求位置去查词，于是删掉的词会被高亮。
- 从时间轴选中的词会滚进视野，但**已经在本屏的不滚**——点词本身就在改选区，
  每次都滚会把它从指针底下移走。比视口高的行（这个栏宽下很常见）反过来判「是否已铺满
  屏幕」，否则它永远不算完整可见，每点一个词都滚一次。
- 气泡锚点带上它所属的 `{from,to}`，选区被别处改掉时气泡自动收起，避免「飘在一个词上方、
  作用在另一个词上」。

验证：`scripts/check-seek-link.mjs` 九项检查全 true（seek 高亮词 / 不勾方框 / 不缩放、
勾方框跳转且不缩放、点词跳转且选中该词）。tsc、npm test 172、pytest 725、vite build 全绿。

**又一个走查上的坑**：第一版脚本用 `window.innerHeight` 判断元素是否可见，而下面压着
「操作记录」面板，坐标点下去打到了它的 `H3` 上，日志里出现的命中元素是「H3 操作记录」。
现在每个候选点都先用 `elementFromPoint` 核对，命中的不是目标就跳过。
## 点完时间轴后字幕区滚不动（2026-11-10）

上一轮加了「点时间轴 → 高亮对应词 → 如果它不在屏上就滚过去」。上线后用户报：
**点完时间轴，字幕区被锁在那句话上，滚一下就自己跳回来。**

根因是一行看起来无害的代码：

```ts
const range = selectionRange(selection);   // 每次渲染都新建一个对象
```

`selectionRange()` 返回 `{from, to}` 字面量，所以 `range` 的**引用**每次渲染都变。
而「把选中词滚进视野」那个 effect 的依赖里有 `range`——于是滚动引起的重渲染
（`onScroll` → `setScrollTop`）把它又唤醒了一次，它重新发现选中的词已经不在屏上，
就滚回去。滚一下、弹回来、再滚一下、再弹回来。

**这个 bug 的教训不在 `useMemo`，而在判据的位置放错了。** 那个 effect 想表达的是
「**选区变了**时，把它带进视野」。可它写在 effect body 里，靠 `rowVisible` 去猜
「是不是用户自己滚走了」——而 effect body 根本没有能力区分这两件事：走到那一行时，
「用户刚滚走」和「选区刚移过来」的状态完全一样。「选区变了」是**依赖**层面的信息，
必须落在 dep 数组里，不能等到 body 里再判断。

实测（`scripts/check-scroll-lock.mjs`，真实滚轮事件）：

| | 点时间轴后 scrollTop | 再滚四下 |
|---|---|---|
| 修之前 | 33303 | 32646 → **32646 → 32646 → 32646** |
| 修之后 | 34570 | 34810 → 35050 → 35290 → 35530 |

修之前那一步 `-657` 正是弹回：滚轮把位置推到 32886，effect 把它拉回居中位置 32646。
四步全都「不同于基准值」，所以只比较「和初始值不同」的检查会判成正常——检查必须看
**相邻两步之间**有没有真正前进。

修法两条：

1. `range` 用 `useMemo` 包住，依赖 `selection`。
2. 把「哪些 token 属于哪一行」抽成 `rowOfToken()` 放到 `transcript.ts` 里，带测试。
   它和 `tokenAt` 一样是半开的：`[40,47)` 的句子拥有 40–46，47 属于下一句；
   差一格就会滚到邻居那行，看起来像「滚错了句子」而不是像算术错。

顺带清掉了那个 effect 里没用到的 `tokens` 依赖。

## 视频 P1：从提案到能导出一条片子（2026-11-11）

上一轮把 §19 的设计写完了（`cf6e532`），这一轮把它做出来：锚点接线、视频区界面、在真机上
渲染、以及三个只有真机才会暴露的问题。

### 一批数字先放这里

在这一轮开始前，我拿两个真实项目量了「视频块边界吸在句子边界上」到底会不会卡住常规剪辑
（1074 句，400 行删除记录）：

| 删除和锚点的关系 | 次数 | 占比 |
|---|---|---|
| 从锚点**开始**（句首整句删） | 254 | 23.65 % |
| **跨越**锚点 | 28 | 2.61 % |
| 恰好在锚点前结束 | 1 | 0.09 % |
| 完全没碰到锚点 | 791 | 73.65 % |

我原本的规则是「边界落在句子起点上的那句话禁止删除」。按这个数据它会锁死 **23.65 %** 的
常规操作——而 254 次里绝大多数是「这句废话删掉」，正是用户最常干的事。所以规则收窄成
**任何删除都不拒绝，编辑后按需重吸附**。

另外量到「整块音频被删光」：1074 句项目里有 **81 句（7.54 %）**。这类块的成片时长是 0，
`map_range` 返回 `None`。不能静默丢行，所以块上带 `orphaned` 标记，UI 给两个动作。

### 锚点接线：两种编辑，两种处理

删除/恢复**不移动任何 token**，所以句子起点网格原封不动，块变短是**读的时候算出来的**
（`view_items` 用 EDL 的 keeps 求和）。这一条决定了删除路径**不需要**重算 EDL——那个按键
必须立刻响应。

边界编辑（切句/合并）会改网格；整片平移是刚性的，块应该跟着平移同样多。

这里踩到一个真问题：第一版 `renormalize` 把**所有**块边界都吸回网格。可用户可能故意关掉
吸附、把边界放在句子中间 40 ms 处——那样一次切句就会把他手工调的位置全部改写，而且他找不到
是哪一步动的。改成 `renormalize(..., previous=旧网格)`：**只有原本坐在某个起点上的边界才
会被移动**。调用方在编辑前用 `grid_before()` 取一份。

### 真机渲染暴露的三件事

**① 模板资源的 URL 少了 project 段。** 路由是 `/{project_id}/video/template/asset/{name}`，
而第一版拼出来的 URL 是 `/api/video/template/asset/background.png`——形状完全合法，响应里
也看不出问题，只是取的时候 404。所以 `test_video_template_assets.py` 的写法是**取响应里返回
的那个 URL 去 fetch**，不是自己拼一个。

**② `find_font("Microsoft YaHei")` 谎报字体缺失。** 原来只做子串匹配，而微软雅黑的文件名是
`msyh.ttc`，`"microsoftyahei" in "msyh"` 是 `False`。于是明明装了，却报「找不到字体，请先
安装」——比不检查更糟，因为给的是错建议。加了一张 family → 文件名 的表，子串匹配降为兜底。

**③ 中文长句 libass 根本不断行，而且一声不吭。** 这个最值得记。

`WrapStyle: 0` 只在**空格**处断行，中文没有空格，于是整句被画成一行任它溢出画布。52 px 时
溢出量小，看起来只是「有点宽」，所以一直到我在真机上把字号拉到 88 px 才暴露：**第一个字和
最后一个字都被裁掉了**，画面像字体 bug。

修法是自己算每行容量。CJK 一字一个 em，ASS 的字号单位就是 PlayRes 单位，所以这是除法不是
测量：`(play_w - margin_l - margin_r) // font_size`。实测 1920 宽、左右各 120、52 px →
`1680 // 52 = 32` 字，与真实渲染逐字对得上。断行优先在标点后，没标点硬断，**绝不为了放下
而丢字**；每行分别转义后再拼 `\N`。

顺带把 `margin_v` 的语义写清楚：它是**字幕块底边**到画面底边的距离，两行字幕从底部往上堆，
所以调大是整块往上抬，不是行间距。

### 视频区界面

菜单 `设置 → 显示视频区` 打开，**默认收起**：多数时候先剪音频，一个没开的功能不该在每次编辑
时都占高度。收起时是一行摘要——「模板已套用 · 4 个素材块」。

块上**必须同时有两个长度**：`原始 10.0s / 成片 8.0s`。只给一个数，用户就会觉得「我明明设了
10 秒」。这里有个容易搞反的点：**块宽度只能用 `duration_ms` 画，不能用 `output_ms`**——用成片
长度画，两个共享边界的块会在其中一个被剪过之后裂开一道缝，看起来像「这里没有视频」，其实它
一直在播。

画廊按 B 语义（比例缩放、轮数不变）显示成 `8 张 · 每张 1.8s（原 2.0s）`。不写「原 2.0s」
的话，删 1 秒让 8 张图各快 12 %，用户看到的是「画面自己变快了」。

字号/留白两个滑块放在静帧下面、不在设置里：「拖一下、看一眼」的中间过程放进对话框要来回开关。
滑块只影响**本次预览和本次导出**，不落盘。

孤儿块用删除线 + 「不含音频」，不用红色：红字在说「你弄坏了什么」，而这是用户自己删的音频。

## 视频 P2：素材库与框内轨（2026-11-11）

P1 能导出一条有背景、有字幕的片子，但素材框是空的——块只能通过 API 建。这一轮把「拖进来」
补齐，并且遇到了三个都会产出**看起来合理**的坏画面的问题。

### 素材是复制进来的，不是引用

用户的素材在它原来待的地方：下载文件夹、共享盘、手机同步目录。时间轴指向那些路径只能工作
一次，之后文件夹一动就静默失效，而失败会在导出跑了十四分钟后才以「文件不见了」出现。复制花
几 MB，换来项目自包含——和 PSD 模板早就做的是同一笔交易。

去重按 sha256、**按项目隔离**。同一张截图导入两次是画廊的常规建法（拖进来、想想、又拖一次），
没有唯一约束的话素材库会堆满肉眼无法区分的行。按项目而不是全局，是为了一个项目的删除不会让
另一个项目的时间轴变孤儿。

尺寸和时长用 **ffprobe 读，图片也一样**。带旋转标记的 iPhone JPEG 像素是横着存的，Pillow 报
的是*存储*尺寸，而所有查看器（和 ffmpeg）显示的是转过的。两种素材用同一个工具，意味着素材库
报的宽高比就是渲染器产出的宽高比。

删除时如果还有块在用，**拒绝并点名**（「第 15 秒那个块」）。替代方案是删掉素材然后把块置空
——那会留下一个静默显示不出任何东西的块，用户没法把它和渲染 bug 区分开。

### 框内轨：一条链 + 一次 overlay

「一个块一个 overlay + `enable='between(t,…)'`」这条路是死的：同一类问题在头像那条线上实测过，
1200 段区间拼出 79 KB 表达式，ffmpeg 直接起不来，报的是 `The filename or extension is too long`
——看起来像路径 bug，实际是 `CreateProcess` 的上限。

第二直觉「先把框内容渲成一个文件再 overlay」要多一整趟 x264。这台机器上编码约 11 秒 / 60 秒
成片，一小时片子会多花 8 分钟，白花。

所以段落在**同一个 filtergraph 里** concat 完，只 overlay 一次。图的长度随**段数**增长，不随
片长增长。

三个坑，每一个都能产出「看起来合理」的坏画面：

**① 输入编号由调用方拥有。** 链只写 `[N:v]`，而 `-i` 列表里背景占 0、美术层各占一个。偏移
算错会把**描边当成框内容**画出来——不报错，画面甚至说得过去。

**② 标签必须按位置取。** 同一个文件可能在一段链里出现两次（画廊同一张图放两遍、空档三次用
底图）。按输入号命名标签会让两个滤镜共用标签，报错是 "label already used"，指向一个变量而
不是原因。

**③ 空档必须显式填。** overlay 的输入短于成片时，overlay 提前结束、画面冻在最后一帧。用
**底图自身的框内裁剪**填空档，既保证不透明、又保证和底板逐像素对齐——这也是为什么不需要一张
单独的「空框」图。

还有一条只在预览上出现的：静帧只声明**覆盖它**的那一段，而 plan 里的 `input_index` 是整条链
里的编号。直接传进去会得到 `Error binding filtergraph inputs/outputs: Invalid argument`——这个
报错既没提素材框也没提预览。预览要重新编号为 0。

### 画廊按比例缩放，账要算对

`output // n * n` 会漏掉 `output % n` 毫秒。那点零头在 37 张图的画廊上足够让框内容比块早结束
几帧，而早结束的表现是**最后一帧冻住**，不是黑屏——所以很难看出来。改成从累积权重取整，
每段边界都对，最后一段锚到精确终点。

### 前端：宽度只能用原始时长

块按 `duration_ms` 画，不按 `output_ms`。用成片长度画，两个共享边界的块会在其中一个被剪过
之后裂开一道缝，看起来像「这里没有视频」，其实它一直在播。成片占比改成块底部一条填充条。

落点没有固定的默认长度：先吸附到句子起点，再跑到**下一个**边界。固定 5 秒对任何素材都是错的
（插话式的两句 3 秒，下一个话题 40 秒），而且它**绝不与已有块重叠**——重叠的块会被链裁掉大半，
看起来像「拖进去没反应」。

拖动保持长度、只吸附起点；拖到两个边界之间就停在那里，不重吸附——把它吸回去等于把用户刚拖到
的偏移悄悄改掉。边缘手柄命中半径用 8 **像素**而不是百分比，因为同一个块放大时 400 px、
缩小时 4 px。

### 走查踩到的两个坑

**HTML5 拖放不能用鼠标事件序列驱动。** 真实拖拽会话是浏览器级特性，不是一串 pointer move。
第一版走查用 `mouse(down/move/up)`，`dragstart` 根本没触发，脚本得出「拖不进去」的结论而功能
一次都没跑过。改用 CDP 的 `Input.dispatchDragEvent`。

**改的过程中发现一个真 bug**：`onDragOver` 原来只在 React 的 `draggingAssetId` 有值时才
`preventDefault`，而拖拽会话可能在那次 state 更新渲染之前就开始了——结果是拖放目标拒绝了自己
正在高亮的那个拖动。现在只认 `dataTransfer.types`。

## 头像亮暗：绑定、明暗轨、以及两个 P1 遗留 bug（2026-11-11）

**绑定必须存在自己的列里，不能塞进 `slots_json`。** `slots_json` 每次编译都从 PSD 重写，绑定
放在里面的话，用户重新导入一次同一份 PSD（改了个颜色，很平常）就会静默丢失，症状是几轮之后
「头像不跟着说话了」而界面上没有任何提示。

**一个头像一条明暗轨，不是一堆 overlay。** `enable='between(t,a,b)+...'` 在 1000 段时把命令行
撑到 79KB，ffmpeg 起不来（Windows 32,767）。改成把「亮」「暗」两张小 PNG 按说话区间用 concat
demuxer 拼成一条 236×249 的 RGBA 小视频，整条只 overlay 一次。实测 14 秒 / 6 段 → 图 441 字符。

**如果绑了人，底图要换成 `background_bare.png`。** `background.png` 里压着 PSD 自己的照片，
暗头像会是「亮照片上盖一层暗」，变成暗得不够。切换是安全的：裸底 + 四个亮 PNG 按槽位重合成，
和 `background.png` **逐像素相同（0 个差异）**，所以在没人绑定之前画面完全不变。

**修掉 P1 的 dim bug：暗头像背后有个灰方块。** `dim_photo()` 按照片矩形压暗，而那个矩形底下
压着头像组自己的白色承板。现在先用「去掉 smart object 的组」合成一张底，把**颜色或 alpha 变了**
的像素当成照片本体，只压这些。两次修正都是量出来的：只比颜色时白色描边被漏掉（底图在那里的
RGB 是纯白、alpha 是 0，所以「没变」），整个人像撒白点；加上 alpha 比较后承板角落从
`(129,128,128)` 回到 `(252,247,244)`。

**修掉 P1 的第二个 bug：`BoxChain.input_count` 恒为 0。** 它读 `len(self.sources)`，而 `sources`
在媒体层永远是空列表（真路径在服务层）。P1/P2 没人读它所以没暴露；P3 要在这个数之后编号头像
输入，算出来是 `[2:v]` 而实际是 `[2:v]`/`[3:v]`，差一位的后果是
`Error binding filtergraph inputs/outputs: Invalid argument`——既没提头像也没提框。现在由
segments 自己数。

### 量出来的四条 concat demuxer 规矩

1. **每个 duration 向上取整到整帧**（1.500 秒 → 1.520 @25fps），所以是**累计取整**：每段写的是
   两个取整后边界之差，否则几百段之后会漂移成秒级。
2. **最后一段要再列一次**（不带 duration），否则它的时长不被采纳——实测 3.00 秒的脚本只出 2.56 秒。
3. **路径必须是绝对的**：demuxer 相对的是脚本所在目录，不是进程工作目录。
4. **不能带 BOM**：带了会报 `Line 1: unknown keyword 'file'`，点名关键字而不是编码。

用 **qtrle** 而不是 PNG 编码：同为无损，600 秒 / 1200 段 PNG 要 5.9 秒 / **338 MB**，qtrle 只要
**1.5 秒 / 55 MB**。

### 238 页不是阈值取错，是规则错

第一版按设计文档写：「遇到 ≥1.5 s 的停顿就断，或者超过 90 字就断」。拿真实项目一跑，
61.5 分钟出 **238 页**——每页 15 秒。先怀疑阈值，量了一下：

| 指标 | 实测 |
|---|---|
| 句数 / 字数 / 时长 | 583 / 17,294 / 61.5 分钟 |
| 句间停顿 p50 / p75 / p90 | 320 / 520 / 830 ms |
| ≥1.5 s 的停顿 | 一小时 **12 次** |

也就是说「遇停顿就断」在这个说话人身上几乎从不触发，实际生效的只有「超过 90 字就断」——
而 90 字只有 19 秒的语音。所以问题不在 1.5 s，在**用字数和停顿当分页依据**。

改成按时长，两个阈值配合：

- 跑满 **60 s** 就断（保证页数随时间线性增长，不随停顿数量爆炸）；
- 已经跑满 **45 s** 且后面有 **≥700 ms** 停顿，就断在自然缝上，不等硬上限。

同一份素材变成 **60 页**，页长 p10 54 s / p50 63 s / p90 71 s。这个「断在缝上」比单纯
60 s 硬切只少几页，但页边界落在停顿上的比例高得多——读起来是「一段讲完翻页」，不是「话说到
一半翻页」。

**说话人变化故意不作分页依据。** 那期轮流发言 320 多次，按人断会得到每几秒一页。问答是一段
话题，不是两段。

### 排版：换行规则全是量出来的

第一版按宽度贪心换行，然后「把以标点开头的行并回上一行」做后处理。问题在后处理：并回去的是
**整整一行**，于是出现 2.3 倍框宽的行走到了画面右边缘——量像素是 `ink x 42..1266`，最后一列
有墨。改成在**断点处**调，四条规则各对应一个真实页面上出现过的错：

1. **闭合标点悬挂**：断在「，」前就把「，」留在上一行（多一个字符，肉眼不可见；行首逗号像 bug）。
2. **开引号不留行尾**：真实出现过「比如说《」/「BIBBIDIBA》」——引号在上一行、内容在下一行。
3. **拉丁词不劈开**：`《BI` / `BBIDIBA》`。断点退到拉丁串开头；如果整个串比一行还长就照宽度断，
   否则会退到 0 死循环。
4. **「，」窗口只有 10 %**：搜索整行会切在第一个逗号上，每行只到 60 % 处，版面像诗。

### 两个只有真机才看得见的 bug

**一、PNG 只按 slide id 缓存。** 编辑器要 1267×712 的预览，素材框要 1440×810 的成片——同一个
id，先到的那张被复用。成片里 overlay 把 1267 的图放大到 1440，正文软掉**并且溢出框右缘**
（因为放大后行宽超出了渲染时的框宽）。改成文件名里带尺寸（`{id}-{w}x{h}.png`），
`invalidate` 用 glob 清掉所有尺寸。这个错没法靠单测发现：`render_slide` 的签名里没有任何
东西说「尺寸是身份的一部分」。

**二、页面底部和烧入字幕打架。** 字幕按整帧的 `margin_v`（1080 的 56 px）画，对框里有什么
一无所知。实测最后一行正文离字幕顶端只有 ~10 px，看起来就是文字压在文字上。现在底部预留
**9 % 框高**（810 的 73 px），代价是半行正文。

## 三个缓存键的错，症状都不是报错（2026-11-11）

用户报的是「localhost:5173 102」。那是 dev server 被停掉了，不是代码问题。修完之后顺手查了
交付物里的缓存，找到三个错，**共同点是没有一个会报错**，长的都是「画面没变」：

### 1. 静帧的缓存键里没有样式

`preview_still` 的文件名是 `still-{at_ms}.png`。改字幕字号会把新字节写进**同一个 URL**，
前端 `setPreviewUrl` 也传同一个字符串，React 没有 DOM 变更，浏览器就不会重新请求。
用户的感受是「拖字号，点生成静帧，画面不动」。

实测（CDP）：连按两次「生成静帧」、中间把字号从 52 拖到 88，
`performance.getEntriesByType("resource")` 里 `still-` 只有 **1 条**。

修法是让文件名带上产生它的输入，而不是在前端加时间戳 —— 前端加戳会把「同输入同文件」这个
性质也一起破坏掉，缓存就永远命中不了：

```
still-{at_ms:09d}-{digest}.png
digest = sha256(样式 | 时刻 | 覆盖该帧的框段 | 该时刻的头像亮暗 | 绑定)[:10]
```

摘要只取**这一帧**依赖的东西：框段而不是整条时间轴，所以移动一个不在这一帧里的块不会让所有
静帧失效。修完实测：52 → 88 → 52 得到两个不同的 URL，回到 52 又拿回原来那个；
浏览器请求数 1 → 2。

### 2. 导出的签名里没有头像绑定

`_video_signature` 的注释写的是「everything that can change the pixels or the audio」，
但 `bindings_json` 不在里面。当时没炸，因为 `start_export` **每次都排队重新编码**，根本不复用，
签名只是记在 `edl_hash` 列里没人读。

这正是最坏的一类坑：签名存在的意义就是复用，复用一上线，改头像绑定就不会重新渲染，而且
没有任何报错。已补 `bindings_json`、`deck_id`（演示稿换了内容也要重编码）、在场头像的名字。
新增 5 条测试钉住「改绑定 → 签名变」。

### 3. 「重新生成」把 PNG 漏在磁盘上

`clear_slides` 只删行不删文件。一次「重新生成」之后每个页面的 id 都是新的，旧图片再也
没有任何东西能指向它们。实测在一份 60 页的 deck 上：**62 个孤儿文件 / 14 MB**。

第一版修法只按「这次要删的那些 id」清理，实测跑完仍是 62 个孤儿 —— 上一次出错时留下的那些
已经没有行能命名了。最后一版：**换掉全部页时直接清空整个目录**（这目录只属于这一个 deck），
单页删除才按 id 清。修完实测 `png 123 → 0`。

`delete_slide` / `clear_slides` 的 `settings` 参数因此从可选变成必填：图在磁盘上，行不知道
它在哪，**每个调用方都必须能说出来**。可选参数正是上次漏掉它的原因。

### 验证

- 后端 1134 passed / 1 skipped / 3 deselected，`ruff` 干净，`mypy --strict` 95 files。
- 前端 219 passed，`tsc` 干净。
- 真机：静帧 URL 随字号变（52/88/52 → 两个 URL）；重新生成后 deck 目录 `png 123 → 0`；

## 工作区改版：抽屉、标签页、两条轴共用一个窗口（2026-11-11）

三件事一起做，因为它们互相依赖：左栏让位之后视频区才有宽度做「预览 + 设置列」；设置收进标签页
之后视频轴才够得着面板底部；轴到底部之后，和音频轴共用窗口才有意义。

### 1. 左栏变成抽屉

三个面板各自能折，但它们加起来是**一个工作区**、共用一条右边框。做视频版面、导出、调设置时，
要的不是折掉某一段，而是整栏让位。所以右边框上挂了一个 14×64 的把手（`‹` / `›`），点一下
收成 0 宽，把手跟到窗口左缘。

两个数字是量出来的：

- **关着时 `left` 不能是 0。** 居中在 14px 宽的元素上，`left: 0` 会让它跑到屏幕外一半（实测
  `left: -7`），可点面积只剩 7px。改停在 `7px`。
- **只设 `grid-template-columns: 0` 合不上。** flex 子项仍按 min-content 撑开，实测侧栏宽度还是
  420px。`.sidebar` 在关闭态加 `visibility: hidden` 之后才是 0。

### 2. 视频区：预览左、设置右、标签页切换

原来 模板 / 字幕 / 素材库 / 演示稿 四段竖着堆，堆完的结果是「要够到下面的视频轴，先滚过四屏
和自己当前目标无关的设置」。现在 `.video-stage` 是两列网格：左边 16:9 预览 + 生成静帧，右边
320px 的设置卡片，顶部四个 `.tab`（与 `ScriptPanel` 同一套），下面只渲染选中那一页。

「演示稿」那页单独放宽到 560px（`.video-stage.wants-wide`）：它是唯一一个**双栏编辑器**而不是
表单的页，320px 会把每个页标题截成六个字。窄于 1180px 时两列堆叠——硬撑两列会让预览先塌掉，
而预览才是这个面板存在的理由。

### 3. 视频轴到底部，与音频轴共用一个窗口

这条是「导入素材不知道放哪」的根因，不是排序偏好。`VideoPanel` 原来自己持有

## 2026-11-12 演示稿的标题和正文字体分开设

用户一句：「目前 ppt 文稿没有字体设置，增加一下。标题和正文可以分开设置字体。」

**原来根本改不了，不是改得不好。** `slide_render.FONT_FAMILY = "Microsoft YaHei"` 是模块常量，
`core/slide.layout` 也只有一个 `measure`，标题和正文都拿它量。模板页（§19.14）早就分三个字体
设了，演示稿是产品里唯一一处「字体全有或全无」的地方——偏偏它最需要分级：一页的标题和它下面
的要点不是同一种文字。

**分开的不只是两行代码，量宽度那步也得分开。** 字宽不可互换：同一句标题用雅黑量「放得下」，
换黑体画出来就过右边界。所以 `layout()` 新增 `title_measure`（`None` = 两者同字体，旧行为），
标题换行、缩字号、块高度全走它。`render()` 里那个字体缓存原来按**像素字号**索引，两个角色各取
字体后 60 px 会撞在同一个键上，「标题黑体 + 正文雅黑」会静默变成同一个字体——设置看起来生效了，
只是画出来是错的。现在键是 `(family, size)`。

**存两列，空串 = 跟随默认**（迁移 `a7c3e9f14b26`：`deck.title_font` / `deck.body_font`）。存族名
不存路径（字体可能重装、可能从字由重下）。空串的后果是刻意的：存量 deck 像素逐字节不变，默认
值留在代码里而不是写进 30 行数据库，以后换 `FONT_FAMILY` 时没被用户动过的 deck 会跟着换。
改动走 `PATCH /api/projects/{id}/deck`，不是按页：字体是整份稿的属性，像 PPT 母版。

**缓存文件名必须带字体**：`{slide_id}-{w}x{h}-{标题}+{正文}.png`。换了字体而 URL 不变、文件不变，
浏览器和素材框都会继续给旧字体（§19.11 陷阱 24 已经为「改文本不重画」收过一次账）。`set_fonts`
同时清空整个目录——旧字体那批文件按新名字再也叫不出来，除了这次清空没有第二个地方会收。空串
在进文件名前先解析成实际族名，所以「没设过」和「显式选了默认」是同一个文件；不这么做，从下拉框

**第 1 条：`crop` 默认取中间，而中间是错的。** 主体在上面（标题栏、人脸、logo），溢出的
是页脚和空白；居中裁把上面裁掉、把下面那块空白留着。改成锚在左上角（`crop=w:h:0:0`），
横向同理。`blur_fill` 的模糊背景也是 `cover`，一起改——两处不一致会让背景和前景显示同一张图
的不同部分。

这是渲染事实，所以验证也是渲染的：`.tmp/o1_covercheck.py` 用真实链路渲一帧，一张上红下蓝的
竖图，**居中 = RGB (47,0,207)（大面积蓝，主体没了），左上角 = (253,0,0)（全红）**。

**第 2 条要先解决一件事：素材的声音从来没进过成片。** 视频轨只产出无声视频（`-map [vout]`），
最后 `-c copy` 贴的是播客成片音频。一个只写标记的 M 会是「什么也不做的按钮」。所以先按你选的
默认值做**默认静音**：`video_item.muted` 默认 `true`，没按过 M 的项目导出的听感和以前一模一样，
**全静音仍然走 `-c copy` 不重编码**。

混音这一路三个坑，都是实测的：

| 坑 | 实测 | 处理 |
|---|---|---|
| `amix` 默认按输入数平分 | 一按 M 播客音量减半 | `normalize=0` |
| 两个满幅信号相加 | 96000 采样里 **36000** 个顶在 16 bit 天花板 | `alimiter=limit=0.95`（峰值 31130，0 个顶死） |
| `alimiter` 默认延迟 | 冲激测得 **239 采样 = 5 ms** | `:latency=1`（实测延迟 0） |

5 ms 很小，但它是素材画面和声音之间的**系统性**偏移——这个项目在别处最不肯将就的正是这一类。

`has_audio` 在导入时问 ffprobe（`video_asset.has_audio`），因为渲染时再探就是每次导出对每个
不同片段起一个进程，而界面根本猜不出来。已有的 6 个片段用一次性回填补齐（24 个里 6 个有声音）。
气泡里的 M **只在有声音的块上出现**：永远灰着的按钮等于在问「这块哪里坏了」。

`muted` 进了导出签名。否则按下 M 之后，缓存会把上一版音频原样还给你，而且没有任何提示。

**第 3 条：`Shift+←/→` 只动一边。** `Ctrl+←/→` 挪整块（长度不变），`Shift+←/→` 只把这一边
拉到邻居上（长度改变）。同一个邻居搜索，相反的动词。

**踩到的坑值得记：** 第一版守卫检查新的整段跨度，而真实数据里存在只重叠几毫秒的块（演示项目

**说明行砍到只剩快捷键。** 原来讲拖两端、拖块身、滚轮、Shift+滚轮——全都能靠试出来，而且缩放

## 2026-11-13 第五种填充方式「模糊裁切」

用户：「增加一个新的填充方式：模糊裁切。是按原图片像素宽度摆放，以顶边中点为锚点，超出部分
裁掉，同时素材框里没满的部分用模糊填充。」

三条规则，每一条都是对已有策略的一次刻意偏离：

| 规则 | 和谁不一样 | 为什么 |
|---|---|---|
| **完全不缩放** | 其余四种都会缩放 | 唯一为「必须保持像素清晰」存在的模式：1080 宽的截图进 1440 的框，多出的 180 给背景，而不是放大 1.33 倍糊掉 |
| **顶边中点对齐** | `cover` 是左上角 | 宽图两边各裁一半，高图只裁下面；左上角会只剩右边那半 |
| **没满处模糊填充** | — | 截图旁边一条纯黑读起来像渲染坏了 |

`overlay` 自己会裁（框外不画），这就是「超出部分裁掉」那一半。前景那句 `setsar=1` 不是装饰：
像素宽高比未知时 `overlay` 会**重新缩放**输入，而「1:1 摆放」正是这个模式的全部意义。

背景链抽成 `_blurred_backdrop` 供 `blur_fill` / `blur_crop` 共用——两份拷贝迟早会漂成两个功能。
抽的时候抓到一个 bug：helper 原来自己拼输出标签，而 `blur_fill` 的下游引用的是
`[bgbase{label}]`，一个没人定义的标签，报错发生在编码时（二十分钟之后）。

**验的是像素，不是字符串。** 字符串匹配只能证明参数写下来了。真实链路渲一帧，拿一张 700×600
的 2 像素竖条纹图（锐利内容 = 高频），量锐利区在哪、有多宽：

| fit | 锐利列 | 宽度 |
|---|---|---|
| `blur_crop` | 369..1069 | **701** ← 原图像素宽度，一像素没缩放 |
| `blur_fill` | 246..1191 | 946（被放大到框内） |
| `cover` | 3..1435 | 1433（铺满） |

369 正好是 `(1440 − 700) / 2`，即顶边中点对齐后左边缘该在的位置。同时断言两侧不是纯黑。
那个对照组是必要的：没有它，「不缩放」只是在读自己的代码。

## 2026-11-13 随时可以导出：不再要求先剪

用户：「现在导出音频和视频都要求先删除要剪掉的内容。这是个不合理的要求，用户可能用软件只是做
字幕校对然后直接做视频，不一定非要剪音频。应该允许用户随时导出音频和视频。（而且去掉相关的
说明）」

三处「要求」，三种不同的东西：

| 在哪 | 原来是 | 现在 |
|---|---|---|
| 导出菜单 · 成片音频 | `disabled: ... \|\| deletions.length === 0`，提示「先删除要剪掉的内容」 | 只等 EDL；提示回到格式 |
| 导出菜单 · 成片视频 | `videoExportEntry` 里 `deletionCount === 0` 的分支 | 分支删掉，入参里的 `deletionCount` 一起删掉 |
| 服务端视频导出 | 找不到同 EDL 的成片音频就抛 409「先在导出里导出成片音频」 | 没有就自己渲染一份 |

前两条是纯 UI 的墙——EDL 本身一直是对的：**没有删除就是一条覆盖全片的 keep**。第三条是真的
依赖（混流需要一个音频文件），所以拆墙必须同时把那份音频做得出来。`_audio_for` 先按 EDL 签名
找已有 `render` 行复用（这是 `-c copy` 便宜、且成片声音和用户已认可的那条音轨逐位一致的原因），
找不到就现场渲一条并记成 `render` 行——记这一行是为了让之后手动点「导出成片音频」立刻命中缓存。

**音频在 worker 里解析，不在请求里。** `PreparedVideo` 因此不再带 `audio_path`：它在排队那一刻
根本不存在。把 `_audio_for` 放进 `prepare()` 会让 POST 阻塞整个一期节目的编码，也就是把第 42 轮
那个「点击后无反应」和 12 分钟持有 SQLite 写锁换成第 110 轮的衣服。

**验的是一个真的文件。** 演示项目的 `data/app.db` 复制到临时目录，把那版的 `deletion` 行全删掉
（只做过字幕校对的状态），再调原来抛 409 的那个函数：EDL `keeps=1 / removed_ms=0 /
3 695 928 ms`，写出 89.7 MB 的 m4a，ffprobe 量出 3695.90 s，再调一次复用同一文件。整片那条
走公开入口 `start_export`，编码 + 混流 + 字幕烧入全跑，再量 ffprobe。

**顺手抓到一个别的缺陷：`text_overlay._fit` 的循环可能一次都不跑。**
`floor = max(12, round(size * 0.5))`，当 `size < 12` 时 `floor > size`，循环被跳过，函数抛
「这段文字排不下」——既不说是哪个槽，也不说为什么，而且是在成片音频已经渲完之后。触发它的是
2026-11-10 编译的旧 `slots_json`（文字槽没有 `font_size`，被读成 0）。三处改动：`floor` 不得
大于起始字号；缺字号时按**槽高**兜底（第一版只做「不许崩」，渲出来是 617×109 的标题里塞 6 px
的字）；兜底字号不受 0.5 地板限制（否则标题撑成三行 194 px 溢出）。实测同一句标题：6 px 看不清
→ 54 px 三行溢出 → 30 px 两行正好。

## 2026-11-13 · 第 111 轮：素材块 S（顶替播客）与展现方式（素材框 / 全屏）

两件事，都是用户拍板的原话见 `docs/video.md` §19.25 / §19.26。

**S = Solo，M = Muted，一个三态控件。** 都不亮 = 静音（默认）；M 亮 = 素材的声音混在播客下面
（第 108 轮那条路）；S 亮 = **播客这一段被挖掉，换成素材的声音**。实现是给播客加
`volume=enable='between(t,a,b)':volume=0` 再相加——不切开、不拼接，所以播客流长度一个采样
都不变，`amix=duration=first` 仍然决定成片长度。互斥写在 `update_item`（服务端）而不是 UI：
`PATCH {"solo": true, "muted": true}` 不该造出一个渲染器只能猜的状态。

**展现方式作为填充方式之前的下拉。** 默认 `素材框` = 现在的做法；`全屏` = 归一化到画布、
overlay 到 (0,0)。一条链里可以混两种几何：框内段归一化到框再 `pad` 成画布大小的 RGBA
（pad 色 `black@0`，让模板背景透出来）。**没有任何全屏块时走的还是原来那条不透明链**——已有
项目重导必须逐帧一致。气泡上两个下拉都去掉了文字标签，解释放进 `title`。

验的：S 用窄带滤波 + 「只有素材」对照组证明段内播客降到泄漏地板（31 vs 地板 30，段外 731）；
四次真实导出的归一化互相关 段内 -0.003 / 段外 1.000。全屏用真实导出取帧量像素覆盖率，
框外色带 98.7% 的像素被覆盖。
